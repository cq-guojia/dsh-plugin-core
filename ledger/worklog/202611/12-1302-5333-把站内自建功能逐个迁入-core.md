## Background

### 一句话

**本任务只改 `dsh-plugin-core` 这一个仓库。** 兄弟插件里手搓的「通知任务中心」同类实现，是拿来验证 core 够不够用的**需求证据**；要被改的是 core，兄弟项目那些文件不归本任务动。

### 用户口径（2026-11-12，第三次纠正，以此为准）

> 「我跟你说的就是这个项目不要你去管，兄弟项目，听得懂话不？」
>
> 「这个项目核心里面你需要改。」

前两轮的错误：把结论写成「去 tdt / stp / ledger 删哪些行」——那是越界。兄弟项目的现状只能用来回答一个问题：**core 的现有 API 能不能接住这种用法？接不住就补 core。**

### 靶子

core 的通知任务中心：`src/ui/infra/task-notifications.ts`（`notifyTask` / `notifyTask.run` / `notifyMessage` / `taskNotifications` / 句柄）＋ 贴身件 `src/ui/infra/ticker.ts`、`src/ui/feedback/Loading.ts`（`RunningBlocks`）、`src/ui/feedback/Toast.ts`（`notify`）。

兄弟项目里算「同类自建」的只有两类：① 自己维护后台长任务运行态（本地 `busy`/`step`/`closing`、手搓 `setTimeout` 兜底、切页即断、结果只靠一次性 toast）；② 自己渲染一次性提示（直连官方 `Toast`，或 state + 自增 seq + useEffect 重播）。

### 明确不做

- **不改 tdt / stp / ledger 任何一行**——那是别的仓库、别的任务；
- 不是「找 core 该提供什么」（页面骨架、i18n、文档渲染、宿主数据面都与本任务无关）；
- 不给旧协议做兼容层，不给官方组件缺失做降级兜底。

### 历史（为什么走到今天）

**① 通知中心自身的演进**（本任务的前置条件，全在 `src/ui/infra/task-notifications.ts`）：

| 阶段 | 加了什么 | 解决了什么 |
|---|---|---|
| 1 | `notifyTask` / `notifyTask.run` 门面 | 「注册 + 跑 + 结算」收成一个入口 |
| 2 | `settleLocal()` + Web Locks 失联清理 | 页面崩了/关了，任务不会永远卡在 running |
| 3 | 两级分组（协议 2） | 记录形状变了，全局键 / 事件通道 / 锁名前缀一起换命名空间 |
| 4 | 拆出常驻任务与纯广播 `notifyMessage`、`icon` / `iconSvg` | 一次性提示不必伪造一个 task |
| 5（今天 `502ac275`） | `hidden` 静默任务 + `timeoutMs` 回收窗口（按 `updatedAt` 起算） | 兄弟项目那些「手搓 10 分钟 / 90 秒兜底」终于有等价物 |

**② 盘点走错靶的历史**：2026-11-12 第一轮按「demo 页面骨架」盘了 19 项（文档骨架 / i18n / 宿主数据面），用户当场纠正——目标只是通知任务中心那套机制。那份清单**已作废**。

**③ 已迁完的范例**：`packages/demo/src/sections/task-notifications.tsx`——`:2-15` 从 core import，`:74-89` 用 `useSyncExternalStore(taskNotifications.subscribe, getSnapshot)`，`:102-112` 真实调用 `notifyTask(...)` / `notifyMessage(...)`。

## To Do

### 一、core 能力对照（兄弟项目 11 处手搓用法 → core 现在接不接得住）

| 手搓的用法 | core 现有 | 结论 |
|---|---|---|
| 后台长任务 running → done/failed | `notifyTask` + 句柄 `done()` / `fail()` / `isSettled` / `settled` | 够 |
| 阶段文案 / 进度 | `handle.update({ detail })` | 够 |
| 超时兜底（10 分钟、90 秒） | `timeoutMs`，按最后一次活动起算 | 够 |
| 静默跑、不打扰 | `hidden`（默认 5 分钟兜底） | 够 |
| 切页/重开后还在 | 池 + 广播 + `remote` + `settleLocal` | 够 |
| 一次性成功/失败提示 | `notifyMessage` / `notify` | 够 |
| 带按钮的提示卡 | `notify(..., { actions })` | 够 |
| 「连点再弹一次」 | `notify` 本就可重复调用，无需自增 seq | 够 |
| 逐请求 abort | `timeoutMs` + `settled` | 够 |
| **运行中「整块明暗脉冲」视觉** | 只有三块缩放的 `RunningBlocks`（`Loading.ts:96`），无整块脉冲 | **缺一档** |
| **延迟出现的 busy（取数快时不闪）** | `Loading` 只有 `anchorId`，无 delay / 最短停留 | **缺参数** |

结论：11 处用法里 9 处 core 已经接得住，**core 实际缺两样**。

### 二、core 侧待做（两件，需用户拍板）

2. **`Loading` 补 delay**：加 `delayMs`（多久之后才显示）与 `minVisibleMs`（显示后最短停留），默认值保持现状（立即显示、不强制停留）。

### 三、验收（只围绕 core）

- `pnpm run build` + `pnpm test` 全绿（含 `pretest` 的 `gen-css --check` / `gen-docs --check` / 根与 demo 的 `tsc`）；

- 不碰任何兄弟项目文件。
