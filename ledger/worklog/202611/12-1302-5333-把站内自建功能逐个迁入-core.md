## Background

### 需求（用户 2026-11-12 原话）

> 「我们不是新做了通知、消息和订阅的这一套吗？原来有一些东西是自己写的，没有放到统一的系统里来。有的是手搓的，有的可能是自己去轮询的。」
>
> 「这些应该用我们这套能提供更好服务的系统，都应该切到整个中心里面来。就是整个这套机制，能管的就不允许再出现第二个跟他差不多的东西，明白了吗？」
>
> 「所以说，你得一个空间一个空间去找，一个方法一个方法去找，然后给我一个列表。」

### 一句话

**在本仓库 `dsh-plugin-core` 内部**，把那些自己手搓的提示、自己轮的询、自己管的后台任务态，全部切到 core 自己的通知任务中心；这套机制能管的，**不允许再存在第二套差不多的东西**。

### 硬边界（已反复走错，写死）

- **只管 `dsh-plugin-core` 这一个仓库**（`src/**`、`packages/demo/**`、`scripts/**`）；兄弟项目一个字不提、一个文件不碰，它们不在我的权限内。
- **不是**「找 core 该提供什么」（页面骨架、i18n、宿主数据面都无关）。
- **不是**视觉细节：运行中的呼吸动画（明暗脉冲）、取数转圈何时出现（延迟显示 / 最短停留）都**不是**通知机制，已移出本任务，不再讨论。
- 用户复述需求时确认的口径：「换回来」= 切到通知 / 消息 / 订阅这一套中心来（不是退回旧版本）。

### 判据（满足任一条就是本任务的对象）

1. **自己弹提示**：自己 `useState` 存一条提示 + 定时器/effect 管它什么时候消失，或自己渲染官方 `Toast`。
2. **自己轮询**：`setInterval` / 反复 `setTimeout` 去取数或刷界面，而 core 已有 `ticker` / 订阅通道可管。
3. **自管后台任务运行态**：本地 `busy` / `step` / `loading` + 手搓超时兜底 + 手动结算，结果只靠一次性提示。
4. **第二套事件 / 订阅通道**：自己搭 pubsub / EventTarget，与通知中心的事件总线重复。
