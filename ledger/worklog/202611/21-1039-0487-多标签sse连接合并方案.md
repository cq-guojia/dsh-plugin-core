### 方案 v1（待交叉复审）

**A. 定位与边界**
- 新 `src/adv/tasks/shared-stream.ts`：唯一负责选主 / 扇出 / 晚加入同步 / failover。`stream.ts`（解析 + 退避）、`host/task-stream.ts`（三流 / 基线 / 保活 / outbox）都不动协议。
- 「一条长连接」的准确含义：**每个 `streamUrl`、每个同源浏览器上下文族，本插件恒 1 条常驻 SSE**，其上承载全部三种推送帧（`task-snapshot` / `task` / `task-notice`）。submit 保持独立短 POST——SSE 单向，POST 请求结束即释放 socket，不占连接池常驻名额，且合并它需要新增长连接双向通道，反而增加服务开销。宿主 `follow`、其它插件、不同浏览器/设备不在 core 可控范围。

**B. 选主（Web Locks）**
- `navigator.locks.request(<ns>:lock, ...)`，锁名按协议版本 + `streamUrl` 做稳定哈希命名，避免多插件 / 多 streamUrl 碰撞。owner 在持锁期间跑 `connectTaskStream`，锁回调挂一个 Promise，直到 dispose 才 resolve → 锁释放 → 等待者自动成为新 owner（标准 sse-coordinator 模式，标签关闭 / 崩溃自动 failover）。
- 每届 owner 生成唯一 `epoch`；帧带 `{v:1, kind, epoch, seq, sender, payload}`，独立 wire + `isFrame` 校验，不碰 `NotifyWire`。收端丢 `epoch` 旧帧与同届乱序帧，挡住切主瞬间的迟到帧。

**C. 扇出与晚加入**
- owner 本地 `ingestTask`/`ingestNotice` 后广播；follower 收到后走同一对 ingest 函数（各自 sessionStorage 按 id 去重、各自 origin 判弹卡）。BC 不发给自己（`notify.ts:164-169`），owner 不靠回环。
- 晚加入标签发 `state-request`；owner 用 `taskStore.getSnapshot().tasks` 回 `state-reply` 作基线（幂等，靠 store 单调守卫 `store.ts:154-157`），基线先于增量。
- notice 历史：owner 侧加有界 notice 缓存（建议 512，与 `SEEN_NOTICE_LIMIT` 对齐），`state-reply` 携带，晚加入标签各自 `ingestNotice` 去重。否则丢历史通知 = 影响使用。

**D. 降级（关键争议点，待复审）**
- 浏览器有 Web Locks → 单飞（目标路径）。
- 浏览器**无** Web Locks：不得静默退回各开各的。可选 (a) 不开 SSE + 可见告警（保持「本插件不搞死全站」，但丢实时）；(b) BC 租约选主（仍 1 条，代码更多）。倾向 (a)，但需复审是否算「影响使用」。
- Node / 测试环境（无 navigator）：允许直连 `connectTaskStream` 作为测试专用模式，保证既有测试全绿；不视为产品降级。

**E. 残留闸门修复**
- `api.ts`：让 `connectTaskCenter` 对同一 `streamUrl` 幂等（复用已有协调器 + 引用计数式 disposer），`connectTaskLayout` 返回 disposer 不再丢弃——消除二次接线；`TaskCenterHost` 补 `retryDelaysMs` / `maxLifetimeMs` 并透传。
- `stream.ts`：永久错误零退避改有上限冷却（同 URL 同因才拦）、退避加 jitter、连接寿命上限；`onGiveUp` 默认不静默。

**F. 验证**
- core：`pnpm run build` → `pnpm test` → `pnpm run typecheck` → `pnpm run build:demo`；新增 `test/shared-stream.test.mjs`（内存 lock/channel 假件：N 上下文仅 1 连接、扇出、晚加入基线、切主丢旧帧、disposer 释放锁）。
- 消费端：恢复 `client/index.ts:215-229` 注释 + 两个 import，重建 dist；3 窗口 Network 过滤 `/stream` 仅 1 条 200、Connection ID 唯一；反复改名不卡、pending 请求发出的 Connection ID 非空；A/B 窗口各按 origin 弹一次、notice id 不重弹。

### 第 2 轮：交叉复审 v1（架构+后端 / DSH 前端 两视角）

两位复审一致判定 v1 的 (a) 降级违反「不影响使用」，并另找出 BC 基线无 ACK 的失联问题。逐条证据与裁决：

1. **降级 (a)→(b) 必改**。Web Locks 虽在 Chromium/安全上下文普遍存在，但不是可假设的必然；静默退回各开各的违反约束(2)，不开 SSE + 告警直接丢进度/终态，违反约束(1)。裁决：**主路径 Web Locks；缺失时 BroadcastChannel 心跳租约选主（仍 1 条）；两者皆缺才显式告警降级**。BC 租约与 Web Locks 共用同一套 epoch/帧协议，不是第二套机制。
2. **notice 缓存必要**，但写入点必须覆盖「订阅成功时 outbox 回放那批」（否则补偿不完整）；`scope` 必须随帧原样保留、收端各自按 origin 判定。服务端 outbox 仍是权威，缓存只补晚加入窗口（上限与 `SEEN_NOTICE_LIMIT=512` 对齐）。
3. **幂等化不破坏兼容**：只读搜索 `dsh-task-dispatch-table` / `dsh-session-title-pattern` 全文 0 命中 `connectTaskLayout/connectTaskCenter`，`dsh-task-reminder` 目录不存在；唯一调用方就是本消费端 `client/index.ts:228`（返回 void 被丢弃）。改返 disposer 是纯增量。
4. **viewer 要进分组键**：当前 `authorize: () => TASK_CENTER_VIEWER`（`dsh-task-ledger/packages/plugin/src/index.ts:157`，常量 `"local"`）、store 忽略 viewer（`session-job.store.ts:291-303`），故当下不串；但契约允许按 headers 返回不同 viewer，单飞后 follower 会收到 owner viewer 的数据。裁决：锁名/通道名纳入 viewer 指纹（由 `headers()` 派生，可显式覆盖），不同 viewer 各自成组、每组仍 1 条。
5. **基线盖乐观行：守卫挡不住，必改**。单调守卫 `store.ts:154-157` 只挡「旧终态 → 新 running」；本地乐观 running 与基线旧 done 归一到同 key 时会被盖掉。裁决：store 增 `mergeBaseline()`，遇本地待结算乐观键跳过（乐观键在 `api.ts:293-311` 登记、真源增量到达时清除），只让真源增量覆盖乐观行。
6. **v1 漏项：BC 基线无 ACK/超时**。v1 声称「正确性靠基线 + outbox」，但基线本身走 BC；follower 若错过广播又丢 `state-reply` 会永久拿不到基线。裁决：`state-request` 改为「重复直到收到 reply」；owner 定期广播 `{epoch, revision}` 摘要，follower 落后即重拉；增量帧带单调递增 seq，缺口触发全量重拉（`taskStore.getSnapshot()` 是全量真源）。

前端复审追加三条必改：
- **锁活体**：Web Locks 在后台冻结时不释放；持锁传 `AbortSignal`，断流 / `onGiveUp` / `pagehide` / `freeze` 立即 abort 释放，连接设寿命上限强制重选，follower 心跳看门狗检测 owner 失联。
- **wire 身份**：异插件同 origin 会共 BC；帧带命名空间 + 插件 id，收端比对；`payload` 解包后再过 `isTaskRecord`/`isTaskNotice`（直接喂 wrapper 会被全拒）。禁止经 `deliverNotify→notifyMessage` 重打包回环。
- **scope 原样保留**：`scope:'all'` 各页各弹一次；`scope:'origin'`（`model.ts:43-48`）只有发起页弹——靠各页自己的 `isOrigin` 判定，owner 不代判。

### 第 3 轮终审（首席架构 + 简化性质疑 两视角）

终审判 v2 有三项 P0：① 双模选主（Web Locks / BC 租约）双主双连接风险；② 把 `headers()` 哈希进锁名会因 token 刷新导致单飞失效；③ 缺 owner-ready 握手，owner 首帧未到时回空基线。简化性质疑同时指出 v2 核心增量约一个 `notify.ts`（400–700 行），BC 租约 / notice 缓存 / viewer 指纹 / mergeBaseline 乐观键集合 / 定期摘要可砍。

**裁决（采纳简化，但保留正确性必需项）**：
- **砍 BC 租约**：DSH 是 Chromium + 安全上下文（`https://dsh.nasai.cc:56666`），Web Locks 可用。**只支持 Web Locks 一种选主**；不可用时不开 SSE、显式告警 + submit 本地模式（`api.ts:285`），不静默退回 N 连接、不引入第二套租约状态机（双主风险源）。与「不给缺失做降级兜底」的项目惯例一致。
- **锁名不碰 `headers()`**：`lockName = hash(协议版本 + streamUrl + 命名空间/插件 id)`，稳定不变。前置契约写明「一个 streamUrl 对一个 viewer」——当前 `authorize: () => TASK_CENTER_VIEWER`（`dsh-task-ledger/packages/plugin/src/index.ts:157`，常量 `"local"`）满足；将来多 viewer 由调用方分不同 streamUrl，不为假设场景付复杂度。
- **有界 notice 缓存：v3 误砍，v4 恢复**。终检指出 v3「晚加入丢历史通知」与第 2 轮「丢历史通知＝影响使用」直接冲突，且改变了现有行为（今天每个标签各自连 SSE，各自拿到 outbox 回放，`sessionStorage` 按 id 去重后各弹一次）。**改回**：owner 在 `onNotice` 处把帧写入有界缓存（上限 512，与 `SEEN_NOTICE_LIMIT` 对齐），**必须覆盖建连时 outbox 回放的那批**（否则补偿不完整）；`state-reply` 带缓存帧，follower 解包后各自 `ingestNotice`、各自按 `task.origin` 判 `scope`、各自 sessionStorage 去重。`scope:'all'` 每页各弹一次（符合既定口径），`scope:'origin'` 仅发起页。缓存只在 owner 内存、不落盘、不增加服务端开销。
- **mergeBaseline 简化**：不建乐观键 Set。规则改为「基线只填本地尚不存在的 key」（本地已有行 = 更晚的乐观行或增量真源，基线不得覆盖）。发起页自己作为 follower 时显式业务键（消费端 `close:${taskId}`，`dsh-task-ledger/packages/plugin/src/index.ts:164`）因此得到保护。
- **砍定期 revision 摘要**：与 seq 缺口重拉功能重叠。保留「增量帧带单调 seq，发现缺口即重拉基线」一条。
- **留 owner-ready 握手（P0）**：owner 仅在基线帧全部投影完成后置 `ready=true`；此前 `state-request` 回 `{ready:false}`，follower 持续重发。摘要/响应必须带 ready 位，避免空基线被当成权威。
- **留超时三元组**：帧看门狗 `W = 50s > 2 × keepAlive(25s)`；连接寿命上限（如 10min）到期主动释放重选；`pagehide` / `freeze` / `onGiveUp` / 断流一律立即 `abort()` 释放锁（`navigator.locks.request(name, {signal}, cb)`）。同源标签对 Web Locks 支持一致，无双模即无双主。
- **「所有服务一条连接」口径改写为「所有常驻推送服务一条连接」**：submit 是 GET 响应流无法承载的短 POST，http/1.1 下该 TCP 处于无限响应阶段，无法再发上行；并入需要新端点或双向协议 = 增加服务开销。字面「含 submit 也走同一连接」在约束内**不可行**，明确写进交付说明，不假装达成。

## Conclusion

**方案 v4 定稿**（= v1 核心 + 第 2 轮正确性修订 + 第 3 轮简化裁决 + 终检恢复 notice 缓存）。**本轮只产出方案并逐轮审定，未改任何源码。**

**最终方案摘要**：
1. 新 `src/adv/tasks/shared-stream.ts`：Web Locks 选主（锁名 = hash(版本+streamUrl+命名空间)，不含 headers），单 owner 建一条 `connectTaskStream`；epoch + 单调 seq 帧经独立 BroadcastChannel 扇出；owner 本地 ingest 后广播（BC 不发给自己），follower 解包后各自过 `isTaskRecord`/`isTaskNotice` + 各自 origin 判定 + 各自 sessionStorage 去重；`scope:'all'` 各页各一次、`scope:'origin'` 仅发起页。
2. 晚加入：重复 `state-request` 直到 owner `ready:true`，用 `taskStore.getSnapshot().tasks` 回全量基线，`mergeBaseline` 只填本地不存在的 key；seq 缺口重拉；`ready:false` 期间不把空基线当权威。notice 由 owner 有界缓存（含建连时 outbox 回放批次）随 `state-reply` 补齐，各页按 scope/origin 判定 + 各自去重。
3. 生命周期：`AbortSignal` + `pagehide`/`freeze`/`onGiveUp`/断流立即释放锁；看门狗 50s、连接寿命 10min 上限；旧 epoch 帧/回调一律丢弃。
4. 残留闸门：`connectTaskCenter` 按 streamUrl 幂等 + 引用计数 disposer、`connectTaskLayout` 返回 disposer；`retryDelaysMs`/`maxLifetimeMs` 透传、永久错误有上限冷却 + jitter、`onGiveUp` 默认不静默。服务端 `host/task-stream.ts` 协议与端点不变、**零新增服务开销**。
5. 消费端：恢复 `client/index.ts:215-229` 注释 + 两个 import，重建 dist。

**对硬约束的最终回答**：
- 「不影响使用」：达成——常驻推送全量恢复、归属/去重口径不变、晚加入标签补齐 notice（含 outbox 回放批次）；已知取舍：failover 秒级空窗（基线补齐）。
