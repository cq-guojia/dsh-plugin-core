## Background

DSH 后台结案作业要给 TaskBar 扫光与弹窗 notice 披露进度，两者都读 `TaskRecord.progress.message`（`src/adv/tasks/TaskBar.ts:474`、`src/adv/tasks/model.ts:90-96`）。进度源在宿主服务端进程，客户端 `ctx.report()` 是本地 executor API（`src/runtime/executor.ts:14-17`），跨进程用不上；唯一通道是把进度写进 `TaskRecord.progress` 经 SSE 整条 upsert 下发（`src/host/task-stream.ts:27-38`）。

消费方反馈核心把 progress 当二等公民，逼每个服务端重复兜底五件事：① `carryIdentity` 只保 origin/panelId/settledAt，缺 progress 帧清空文字（`store.ts:105-125`）；② `isStaleAgainst` 只按 startedAt 判新旧（`store.ts:177-182`）；③ `isTaskRecord` 不校验 progress（`api.ts:219-235`）；④ 终态保留无契约而 TaskBar 事实上仍显示（`TaskBar.ts:158-179`）；⑤ 无按 (project,key) 的公共 selector（`adv/tasks/index.ts:4-65`）。

本次调研另查出七条同源缺口：⑥ `upsert` 路径完全不设防（`announce`/`ctx.report` 都走它）；⑦ 三写入路径（upsert/merge/mergeBaseline）合并规则各写一遍；⑧ 本地 `Date.now()` 与服务端时钟不同源（`coordinator.ts:215`）；⑨ 坏 progress 会整帧进 store；⑩ 同 `updatedAt` 无裁决规则；⑪ 无变化也 publish（`sameRecord` 用 JSON.stringify，字段顺序敏感）；⑫ 基线路径同样清 progress。

根因判定：一个字段的合并规则散落在多条写入路径，不是某条路径漏了补丁。业界对标：RFC 7386「缺失字段保留原值」、Kubernetes spec/status 分离与单一写入入口、长任务事件的 per-operation 严格递增序号 + 快照收敛（挂钟只展示不排序）。

## Process

方案交叉讨论与四轮修正（实施前定稿）：

| 角色 | 主张 | 处置 |
|---|---|---|
| 程序开发 | 服务端每帧带全量 progress 即可 | 否决：跨进程用不了 ctx.report，「每帧带」是隐性约定无闸；核心是共享底座应收口 |
| 架构师 | progress 整体 LWW，不做字段级 merge；不新增 seq 字段 | 采纳：message+updatedAt 都是必填，是不可分割快照单元；字段级 merge 会造半新半旧数据；不改 SSE 契约 |
| 前端开发 | 终态文字不能闪、progress 帧不能触发全列表重渲 | 采纳：reconcile 做无变化短路，不靠 TaskBar 绕过 |

四轮交叉验证修正：
1. 把 updatedAt 守卫放进 isStaleAgainst ⇒ 漏 upsert 路径（announce/report 裸奔）。改放进统一 reconcile，两守卫正交：isStaleAgainst 管运行身份整帧，reconcile 内管字段级进度新旧。
2. isTaskRecord 校验坏 progress 就整帧拒收 ⇒ 可选字段坏毁整条任务状态，健壮性倒退。改 sanitizeTask 分层：必填坏拒收、progress 坏剥离。
3. 直接拿 Date.now() 比 ⇒ 本地/服务端时钟不同源。加契约「同 key 严格递增」+ 本地 max(now, old+1)；服务端责任写进接入指南。
4. selector 只返 progress ⇒ API 窄化。改返回整个 TaskRecord，挂在已导出的 taskCenterStore 上，导出面不变。

架构师复审追加：getBaseline 外泄本地 progress 由对端 LWW 裁决（服务端更大 updatedAt 会盖回），可接受并注明；同 updatedAt 内容不同视为服务端违反契约，明确 last-wins 确定性兜底。
