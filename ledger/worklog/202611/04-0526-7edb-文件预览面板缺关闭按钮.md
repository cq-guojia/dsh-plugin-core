## Background

dsh-task-ledger 报缺陷（请求原文落在该仓库 `core-file-preview-close-request.md`，核实版本 `dsh-plugin-core@0.27.0`，本仓当前代码已是 0.28.0）：

- 会话预览里点「变更文件」卡 → 调 `openFilePreview({ mount, content: () => h(ChangedFileDiff, {...}) })` → 右侧 dock 打开、diff 正常，**整个面板没有任何关闭按钮**，只能 Esc。
- 同一插件走 `openFilePreview({ mount, path })`（普通文件）时，✕ 在面包屑行尾，正常。

用户现场确认了这一现象（"点了一下那个修改文件，弹出来的文件预览框右边没有小叉"），并借这个缺陷提出更上层的原则：**消费者在每个环节应该少做事，core 把自己领域的动作做完整** —— 文件预览既然叫"预览文件"，消费者只该给"打开哪个文件 / 哪次改动"，不该自己挑组件、拼节点、补 ✕。"还原"这类动作同理，消费者只给最小配置，核心直接点得开。

**职责划分（M1 会话 / M2 面板 / M3 内容组件 / M4 调用方）核对：**

- 与现有分层一致：`session` 已依赖 `explorer`（`src/session/mirror/MessageItem.ts:16`），反向没有 ⇒ 任何"渲染 diff 的便利入口"只能放 M1，放 M2 就成环。这一条约束成立。

- 缺陷方漏了一个现场冲突：`PanelDock` 的浮动关钮是 `position:absolute; top:6px; right:6px`（`src/ui/side-panel.css:51-54`，20×20），而 review 态 header 右端**已经有换行钮**（`ChangedFileDiff.ts:203-209`）。直接开 `'floating'` 会把 ✕ 压在换行钮上。需要内容右上让位（header 加约 28px 右内边距），这属于"避让"，不违反壳归面板。
- 另：`PanelDock` 的 `closeButton` 默认值 `auto` 本来就是"有头放头、无头浮动"（`src/ui/PanelDock.ts:425-440`），所以不需要给 `DockPanel` 新增什么"无头面板关闭钮"的一等公民，`auto` / `floating` 已够。

## Conclusion

**总判断：缺陷成立、根因判断正确、M1-M4 的切法可用；方案大方向对，但有三处要修。**

1. **关闭钮（必须做，无争议）**：`closeButton` 按模式分 —— 有 `path` 保持 `'none'`（仍在面包屑行尾，位置不变）；有 `content` 给 `'floating'`。**不新增 `DockPanel` 概念**：`auto`（无头即浮动）已经就是这个语义。**选浮动、不做内置头**：`content` 是节点，没有标题，做内置头既多一条横线（违背 2026-10-21 决定），又得让调用方再传 `title`，等于把刚收走的东西又还回去。
2. **`openSessionReview`（建议做）**：`sessionId / seq / index / display` 是会话领域知识，归 M1 正确；调用方从"挑组件 + 塞节点 + 记 handle 补 ✕"降为一行，正是用户要的"最小配置"。参数别另造一套：`{ mount, locator } & Omit<OpenFilePreviewOptions, 'content' | 'path'>`，`title` 缺省取 `locator.display`（顺带补上 content 模式只有 aria-label 没有标题的问题）。
3. **`ChangedFileDiff.onClose` 语义降级（同意，但不许留过渡）**：只保留给 hover 预览之外的旧调用方显式退让，文档写明"关面板不归内容组件"。修完后必须**同一次变更**清掉 demo 的 `onClose`（`packages/demo/src/sections/blocks.tsx:248`），否则同一面板出现两枚 ✕ —— 这比缺陷本身更糟。因此**不需要过渡版本**，也不接受"内容补 ✕"的第二套关法。

**关于"消费者少做事"的原则，我同意但要把边界说死**：判据不是"消费者少写几行"，而是"这份知识属于谁"。

- 属于 core 领域（文件、会话、变更、工作区）⇒ 收进来做成一步调用，消费者只给身份与落点。`openSessionReview` 符合。
- 属于插件自己的业务（任务状态、还原、审批流…）⇒ **core 不认**，只提供它领域内的动作（比如"打开这个文件"）。否则 core 会退化成业务大杂烩，且每加一个插件就要改一次底座。所以 `openFilePreview({ content })` 这个逃生口**保留**，只是不再当推荐路径、文档改推 `openSessionReview`。

**是否 breaking：不构成。** `closeButton` 是内部实现，文件模式行为不变；`ChangedFileDiff.onClose` 不删只降级语义；`openSessionReview` 是新增导出。唯一可见变化是"自己画了 ✕ 的 content 调用方会多一枚" —— 靠同步改 demo + 文档写明"内容组件不得再画 ✕"来兜住，属一次性迁移，不涉及版本号策略。

**待用户拍板的三点**：① 关闭钮走浮动 + 内容让位，还是宁可多一条横线做内置头；② `openSessionReview` 做不做；③ 是否接受"修完即删 demo 自画的 ✕、不提供过渡"。
