## Background

用户真机现象：后台执行任务成功后弹出终态 toast，点 toast 下方「查看会话」按钮，没有跳回发起任务的插件页面，而是弹出「这条任务的操作已失效，可能是发起它的页面已刷新或关闭」。用户操作是「用了后台执行 → 跳到其他页面 → toast 弹出 → 点按钮」。用户诉求：按钮一定是个前端方法，核心应桥回发起页执行它；消费方不该为此改代码。

定位结论（五轮专家交叉验证后）：这是 bug，不是思路错。方向（状态真源在服务端、按钮按纯数据配置、点击时解析 handler、跳回发起页执行）本身成立；坏在 handler 生命周期比 toast 短。

## Process

### 现象与根因链（已核实）

1. 用户最初的怀疑是「id 归一漂移导致 `store.get` miss」——**证伪**。`coordinator.ts:113` 的 `announce()` 用 `store.upsert(final).task` 构造 toast 载荷，id 已是归一后的存活 key；`store.ts:190-202` 的 `mergeInto` 只写不删、byKey 命中写回旧 id。纯 SSE 基线重放不会让 `store.get` miss。
2. 真正原因：消费方 `dsh-task-ledger/packages/plugin/src/client/board-home.ts:257-284` 把 `view-session` handler 注册在 `BoardHome` 的 `useEffect` 里，cleanup 就是 `mountTaskUI` 的 disposer（`api.ts:525` → `store.ts:281-285` 删 handler）。宿主 keyed `main` 槽切面板会**卸载**组件（renderer 用 entry 身份作 React key，`scoped-slots.tsx:1443-1450,369-374`）；toast 宿主却是应用级常驻（`ui-init.ts:35-46`）。于是 toast 还在、handler 已注销。
3. `coordinator.ts:212-225` 的 `press` 先查 handler，查不到在 `selectPanel` **之前**就 `return false`，所以连发起页都不跳。失败文案 `taskbarActionFailed`（`i18n.ts:1194/1779`）把「条目失效」和「handler 缺失」混着说，还臆断了刷新，误导排查。

### 专家讨论与四组反对意见

- 前端专家：handler 注册与 Modal 托管都必须脱离 `BoardHome`（最初方案让消费方改，被用户否掉）。
- DSH 专家：宿主切面板确实卸载；`selectPanel(id)` 若 id === 当前 active 不换 key、无 remount；stale/unregistered id 会抛错。
- 架构专家：服务端零改动（点击路径纯内存）；核心排队方案优于让消费方改。
- 红队四组：① 切走后立刻点会命中未 cleanup 的旧 handler（stale 闭包，view 被旧 cleanup dispose）；② 朴素 pending 破坏 `true === 已执行` 契约、4 条测试断言、不变量 3/4；③ core 内联进每个插件 bundle，模块级 pending 不共享；④ 面板已激活仍无 handler 时 pending 永不 flush。

### 最终方案 P+（裁定后，兼顾全部反对）

只在 `coordinator.ts` 改逻辑，`api.ts`/`TaskBar.ts`/`store.ts`/消费方均零改动：

1. 全局 pending：`Symbol.for('dsh-plugin-core/tasks/pending/v1')` Map，key = `project\0buttonId\0panelId\0startedAt`，覆盖写入去重，上限 32。放全局而非模块级是因为 core 被内联进每个插件 bundle（`notify.ts:8-11`），只有 `Symbol.for` 能跨副本共享（仿 `store.ts:88`）。
2. `press` 分支：task miss → false；查到 handler 但 `activePanelId() !== panelId` → 先 stash 再 `safeCall(selectPanel)` → true（关闭 stale-handler 窗口，与 `docs/api/task-notifications.doc.ts:185-186`「跳回发起面板再执行」一致）；查不到 handler 但有 panelId 且面板未激活 → 同样 stash+跳转 → true；面板已激活仍无 handler / 无 panelId / 无 selectPanel → false（关闭「永不 flush」静默失败，保住 `task-host-adapter.test.mjs:66,67,75,76` 四条断言）。
3. `registerHandlers` 包装：`store.registerHandlers` 后用 `queueMicrotask` drain；每条重新 `store.get` + `isStale` 校验、确认 `activePanelId() === panelId`、TTL 8 秒惰性清扫、按 project 重查 `getHandler`、claim-once（先删后调）、`safeCall('deferred button handler', ...)` 包裹（异常不打断消费方 mount）。
4. boolean 契约诚实保留：`true` = 已执行或已受理且保证在发起页重挂载后执行；无法保证的分支一律 false。不动 `api.ts:302`、`TaskBar.ts:499-507`。

- i18n 不新增 key（失败仍走既有 `taskbarActionFailed`）。

### 残留风险

- 混版：旧 core 不 drain 全局 pending，需消费方同步升级。
- 点击后立刻又切走 → drain 丢弃 pending，toast 已消失，用户看不到二次反馈；如需补可在 `CoordinatorHost` 加可选 `reportDeferredFailure`，仍不要求消费方改。
- 宿主时序无法从代码证实：React 被动 effect cleanup 相对面板 DOM 移除的精确 flush 时机、`selectPanel` 是否同步更新 `activePanelId`（宿主实现不在工作区）。上线前用 Playwright/CDP 在 demo 宿主测「DOM 移除→handler 注销」Δt 与 activePanelId 更新时机，不往产品代码加探针。
