### 需求全文要点（用户原话结构）

1. **例外控件**：允许调用方设置「另外的控件」作为例外，「有可能它不是按钮，有可能是个 input，反正只要是例外，都要把它放出来」；数量与位置不限，`locked` 期间仍可交互。
2. **收起事件**：例外控件里「有一个特殊的事件（比如『收起』）」，点了「我们就会发送到后台去记录一下，然后它就会正常执行，再放到核心的一个统一池子里」；这是「另外的事件」。
3. **事件查看控件（交互）**：「用户可以像使用 button 一样，把这个控件放到某个地方」；控件上显示当前进行中的事件条数；点击展开下拉列表显示正在运行的事件；再次点击收起。
4. **弹窗逻辑**：点列表中的每一条事件「要把那个弹窗给我还回来」；「我不知道那个弹窗是隐藏了还是拉出来重新画，我觉得都可以」。
5. **性能与状态**：「要考虑性能和效率的问题，不能太差，最好是没有什么影响」；「如果它还回来了，就正常在那儿等，再收到下一个」。
6. **结束通知**（用户点名唯一可能麻烦的一处）：「结束是需要用户这边去控制的。怎么个结束方法才能通知到核心，核心才能把这个挪出去？」
7. **统一展示**：A/B/C 都引用本核心时，「每一个收起来的内容，其实都要放到一个统一的地方展示出来」。
8. **分组管理**：默认「直接把项目的名字作为分组名」；「如果项目都叫 A，用户也可以显式地去修改这个分组的名字」。
9. **过滤与显示**：展示控件按项目名过滤 —— (a) 不传 = 全站全显示；(b) 传一个 = 只显示该项目；(c) 传两个 = 显示这两个。
10. **交互形式**：「目前可能只支持弹窗形式，如果能支持其他形式更好，但最少要支持这种弹窗的方式」。

### 需求总表（2026-11-12 第三轮汇总，用户「把我所有的需求再讨论一下」）

下表把首轮十条原话 + 后续各轮追加/修正，收敛成最终口径。**「最终口径」列是本任务的实现依据，聊天记录不是真源。**

| # | 需求 | 最终口径 |
|---|---|---|
| 1 | 例外控件 | 任意 `ReactNode`（Button / Input / 自绘皆可）、1~N 个、位置不限，`locked` 期间仍可交互；其余该屏蔽的照屏蔽，✕ / Esc / 点遮罩三条关闭路径仍封死 |
| 2 | 收起事件 | 例外控件中一个特殊事件；点了由**核心统一出口**登记到后台池，任务继续正常执行。事件载荷只能是纯数据 |
| 3 | 事件查看控件 | 像 Button 一样放到任意位置；显示进行中条数；点击展开下拉列出正在运行的事件；再点收起。计数与展开态属控件本地 |
| 4 | 弹窗还回来 | 点列表条目还原该弹窗；隐藏或重画用户都接受。**只在当页、未刷新、未切页重挂载时可用**；隐藏保树是唯一能保住转圈状态/输入/滚动/未结算 Promise 的路 |
| 5 | 性能与状态 | 影响尽量小；还回来后正常等、再收下一个；多条可堆叠。要求稳定快照引用 + 派生缓存，不允许每次现算新引用 |
| 6 | 结束通知 | 结束由使用方控制，须能通知核心把条目挪出池。**`done/fail` 句柄为主 + Promise settle 兜底**，幂等，成功与 reject 走同一收尾 |
| 7 | 统一展示 | A/B/C 都引 core 时，收起内容进同一个地方展示。靠 `globalThis` + `Symbol.for` 单例收口，不能照抄 `modal-host` 的模块级 `entries` |
| 8 | 分组管理 | 默认用项目名，允许显式改分组名。**core 取不到项目名**（`createStyleKit({id})` 的 id 是每副本私有的 style 标签 id），必须由调用方显式传 |
| 9 | 过滤与显示 | 不传 = 全站全显示；传一个 = 只显示该项目；传多个 = 显示这几个 |
| 10 | 交互形式 | 最低支持 core 自绘 Modal；其他形式（SideSheet / PanelDock / 自定义命令）**本阶段不做**，只留扩展位置 |
| 11 | 跨页 / 跨项目显示 | **及时看见纯数据**，不能点也行。事件驱动、**不轮询**；必须配 baseline 全量状态；不传函数 / 组件 / ReactNode |
| 12 | 跨页点开 | **不做**（用户 2026-11-12 明确接受） |
| 13 | 刷新 / 切页 | 刷新后必点不开；切页导致插件重新挂载同样会丢，用户已知悉 |
| 14 | 数据落点 | **内存**，宿主进程重启即失（用户接受）；**禁止静态文件** |
| 15 | 统一通知 | core 发通知 + core 自己监听 + 消费端可选监听（带参数、他自己处理）；core 内部也用同一套 |
| 16 | 旧机制统一 | 用户明确：以前零散不合理，趁这次统一。**但本阶段先不替换** —— 「先开发，先不要管原来那些东西的替换，等等看，等做好了统一去替换原来的内容」 |
| 17 | 选型 | **暂定 zustand**（用户 2026-11-12「我没问题，那就暂定他了」）。排除 `broadcast-channel`（7 年老项目、star 少）、`mitt`（3 年未更新）、`TanStack Query`（server-state 方向不对） |
| 18 | 硬约束 | 架构健壮、正规、不走歪门邪道；能做就是能做、有坑直说、不强做；界面数据必须真实值，禁止 mock；讨论完成前不动代码 |
