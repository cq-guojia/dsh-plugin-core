## Background

用户 2026-11-15 原话要点：通知任务中心（东西挪到后台的那个）**调不到方法**——只能传数据，函数进不去，
"其实他只能收一个字符串"。真实场景：弹窗提示「收到」→ 收起到后台 → 之后在通知中心点开它想**把它拉回来**，
但拉回来目前没有回调可调。用户提出两条路：

1. **内存栈 + 名字**（用户更想要）：把方法压进内存注册表、给个 ID，条目里只放 ID；
   点条目时自动去注册表里取回方法执行。用户理解成"传的是指针，不占空间"。
2. **全局广播**：点击时发一条带参数的广播，由"当初吊起它的那一方"监听并就地实现处理逻辑。

用户目标（本任务的核心）：「在通知任务中心这整个大的空间里，实现这种方法的传递」——
想调哪个方法就传哪个方法，由中心统一处理，调用方不必自己写监听。
任务要求：先调研可不可行、开发合不合理、有没有成熟项目这么干。

## Process

**当前实现（已核：源码 + docs/architecture/task-notifications.md）**

- `detail` 只收 JSON：函数 / DOM 节点 / 类实例当场抛错（`src/ui/infra/task-notifications.ts:460-468`）。
  跨页是 `BroadcastChannel` + 结构化克隆（`:654-657`、`:761-789`），函数在克隆这一层就过不去。
- `requestRestore(taskId)` 目前只是**在本地事件总线上发一个 `restored` 事件**（`:992-997`），
  没有任何"被调用的方法"；`canRestore` 按 `origin` 判定，跨页条目返回 false（`:991`）。
  ⇒ 用户说的"调不到方法"是事实，不是用法问题。
- 条目在内存、按标签页分片；页面消失靠 Web Locks 判活后整片删除（`:743-759`、`:728-733`）。
  ⇒ 能被看见的跨页条目，它的 owner 页一定还活着（否则分片已被删）。

**可行性结论**

- 函数**永远不能**跨 JS 宿主（标签页/worker/进程）传递；能跨的是"名字 + 参数"。
- 但"指针语义"完全可实现：函数留在本页的 `Map<taskId, fn>`（挂 `Symbol.for` 全局单例上，
  同页跨 bundle 副本共享，手法同 `claimTaskNotifications`，`:378-398`），记录里只放数据。
- 跨标签页时 = owner 页查自己的注册表执行；owner 页已死则条目根本不可见，所以不存在"点了没对象"的死角，
  只需 ack 区分"注册表里没有这个 handler"（句柄被弃但条目还在）。

**外部实证（2026-11-15 抓官方文档 / 源码核对，不是印象）**

| 项目 | 实证事实 | 对本方案的意义 |

| VS Code `commands.registerCommand` | `registerCommand(command: string, callback: (args: any[]) => any)` / `executeCommand<T>(command, ...rest): Thenable<T>`；文档明说 editor 命令参数只允许原始类型 + Position/Range/Uri/Location | 与方案一同构：id 是本进程内函数表，跨进程只传 id 与纯参 |
| Chrome 扩展 `notifications` | `onButtonClicked` 回调签名 `(notificationId: string, buttonIndex: number)`；`create()` 的按钮最多 2 个且只有 `title` | 系统级通知**从不携带回调**，只有 id + 序号；处理器活在你自己的上下文里 |

| `@ebay/nice-modal-react` | 弹窗组件留在 store，靠 id 再挂回 DOM | "收起 → 拉回"的组件层既有做法 |
| DSH 宿主自身 | 题面板收起只是 unpublish，卡留在私有表，回收入口 `userQuestionPanels.reveal(sessionId, callId)`（`docs/dependencies/dsh-host.md:459-461`） | **宿主自己就是按 id 找回，不是靠广播** |

**结论：成熟项目全部是方案一形态**——对象/闭包留在原上下文，跨边界只走 id（或 path）+ 纯参数；
没有一家是把函数序列化过去的（Chrome 通知连函数都没有，VS Code 的命令参数被文档明确限制为原始类型）。

**内部证据（比外部先例更有力）**：池里**已经在按任务存闭包**——`finishers: Map<taskId, finish>`
（`src/ui/infra/task-notifications.ts:602`、`:907`）。再加一个 `activate` 函数进同一张表，
是同一类既有状态多一个入口，不是新机制。

**开销与一致性评估（对应用户四问）**

| 问题 | 事实 | 结论 |
|---|---|---|
| 刷新后方法还在不在 | 池只在内存（`docs/architecture/task-notifications.md:14`：不落文件、不发请求、不轮询）；刷新即整页重建，条目与注册表**一起消失** | 两者同生同死，天然一致，不存在"方法丢了条目还在" |
| 多用户 | 无任何服务端状态；跨页只走同源 `BroadcastChannel`，不同浏览器/profile/机器互不可见（同文 `:141-142`） | 每个浏览器是孤岛，用户数不影响开销；指针就是一个字符串，成本与单用户相同 |
| 服务端重启 | 池不连服务端，重启对它零影响 | 不会出现"服务端重启导致池里方法失效"这种错位；池行只由调用方注册/结束 |
| 处理不了怎么办 | 三种情形分档处理（见下） | 宁可明说"已无法还原"，不静默无效 |

每条的静态成本：一个 Map entry + 一个闭包（捕获该任务持有的 React 状态）；查表 O(1)；
无定时器（过期是写前惰性判断 `:638-652`）、无轮询、无网络请求。点击一次 = 至多一条 `BroadcastChannel` 消息。

"点了调不到"的三种情形（必须分开处理，这是设计而不是兜底）：

1. **owner 页已经没了** → 分片已被删（`:728-733`），条目根本不显示，没有可点的行。
2. **页在、handler 没了**（句柄被丢弃但没 settle，池允许这种状态，`settleLocal` 就是为此存在）
   → 注册表未命中 ⇒ 明确失败，UI 显示"该任务已无法还原"，只保留结束/清理。
3. **handler 抛错或异步 reject** ⇒ 捕获后落到同一条失败提示，不允许异常冒进事件总线（总线本身已 `try/catch`，`:365-374`）。

**方案对比**

| | 方案一：动作注册表 | 方案二：全局广播 |
|---|---|---|
| 调用方写法 | 注册时把函数交给中心 | 自己订阅总线、按参数分发 |
| 绑定粒度 | 任务实例（哪个弹窗的哪个闭包） | 只有名字/参数，靠调用方自己还原状态 |
| 跨页 | 需 owner 页存活并回 ack | 同左，且所有监听者都会收到 |
| 失效判定 | 注册表未命中即可判失效 | 无法判定有没有人处理 |
| 与既有代码 | 复用 `requestRestore` 的位置，加注册表 | 今天已经能用（自己订阅 `restored`），但用户明确不想要 |

**风险清单（实现时必须处理）**

- 注册表键就用现成的 `task.id`（`${origin}:${seq}`，`:863`），不另发明 id。
- 生命周期必须与条目完全一致：`done` / `fail` / `settleLocal` / `dispose` / `pagehide` 都清；
  漏一处就是"闭包攥着组件树"的内存泄漏 + 点击静默无效（未挂载时 setState 不报错也不生效）。
- 别做成全局命令总线：命令是单例，这里绑在实例上。
- `activate` 建议同步返回 boolean（开没开），异步工作自己走；若要异步，`requestRestore` 得 Promise 化。
- 跨页要 ack（否则点了不知道成没成），且 `restored` 事件现在写死 `remote: false`（`:188`），契约要一起改。
- 重入：`publish` → `emit` 是同步的，activate 里若再 `background()` / `update()` 会造成同步重入写，必须隔离。
- 不把执行结果塞回 `detail`：那是数据面，不是命令面。
- 刷新存活是另一个问题：要跨刷新只能把"命令名 + 参数"持久化到服务端（那已经是方案二），
  **保存函数指针在原理上不可能**——这是本方案的硬边界。

**方案 v1（2026-11-15 定稿待实现，用户已确认形态：匿名方法 + 按钮名 + 多个按钮）**

调用方写法（唯一形态，没有第二套）：

```ts
const h = notifyTask('收到确认', {
  detail: { sessionId },                    // 纯数据：列表里显示什么，就放这里
  actions: [
    { label: '重新打开', run: () => setOpen(true) },  // run 是匿名函数，直接给
    { label: '知道了',   run: () => h.done() },
  ],
})
h.background()                              // 收起到后台
```

通知中心渲染：`task.actions.map((a, i) => <Button onClick={() => taskNotifications.runAction(task.id, i)}>{a.label}</Button>)`

契约：

- `TaskNotificationAction = { label: string; run: () => void }`；`run` 匿名，只在注册时给，`update()` 不改动作。
- `TaskNotificationRecord.actions?: readonly { label: string }[]` —— 只存 label，下标即动作 id，所以跨页可见可点。
- 函数进池私有的 `runners: Map<string, () => void>`，键 `${taskId}/${index}`，与 `finishers` 同生命周期
  （`done` / `fail` / `settleLocal` / `dispose` 同路径删除）。
- `runAction(taskId, index): Promise<boolean>`（全 Promise，口径与本仓「异步/确认类 API 一律 Promise」一致）：
  本页条目立即查表执行；跨页条目向 owner 页发 `{kind:'invoke'}`，收到 `{kind:'invoked'}` ack 才 resolve，
  2s 无 ack → `false`。这是全池唯一的定时器，只存在于跨页点击那一刻。
- 失败一律 `false`，不抛异常给调用方；UI 拿到 `false` 显示「该任务已无法还原」并只保留结束。
- `requestRestore` 原样保留（只发 `restored` 事件），文档降级为「没有 action 时的提醒」；新代码用 `runAction`。
- 重入隔离：`runAction` 的调用包在 `try/catch` 里且不参与 `publish` 流程，避免 handler 内 `done()` 引发的同步重入写。

落点：

| 类型与实现 | `src/ui/infra/task-notifications.ts`（`TaskNotificationAction`、record.actions、`runners`、`runAction`、wire `invoke`/`invoked`、`parseMessage` 白名单） |
| 手写契约 | `docs/architecture/task-notifications.md` |

明确不做：按钮图标、动作运行时可改、跨刷新持久化（要跨刷新只能把「命令名 + 参数」存服务端，是方案二）。

**两个专家组评审（独立子代理，只读）发现并已修的真问题**

| 问题 | 处置 |
|---|---|
| `publish(nextTasks)` 用进来前算好的数组写回，`expireLocal()` 递归结算掉的行会被复活成「无 finisher、按钮永远 false」的僵尸 | 改成 `publish(compute)` updater，在 `expireLocal()` 之后再取当前分片（`:758-775`） |
| `finishers.set` 在 `publish` 之后，订阅者抛错会留下无人能收的 running 行 | 提到 `publish` 之前 |
| 分片被删（bye / 判活清理）后 `knownSeq` 不重置，对端同 seq 重发被当旧消息丢弃，该页在对端永久失明（连带按钮永远点不了） | 陈旧判据改为 `seq <= seen && shards.has(origin)` |
| 过期但未被清扫的行仍可点（快照已隐藏、`locate` 仍命中） | `runAction` 前置过期判据 |
| `invoked` 只按 reqId 配对，同源任一页面可抢答 | `pendingInvokes` 记 `target`，ack 必须来自被点名页 |
| `dispose()` 清 `pendingInvokes` 不 resolve，调用方白等 2s | 逐个 `resolve(false)` |
| `locate` 不校验「记录 origin 与分片 origin 一致」，伪造分片可劫持执行路径 | 加一致性校验 |
| `parseMessage` 只判 `Number.isInteger`，`1e300` 能过；`isActionInfos` 允许空 label（与本地校验不对称） | 改 `Number.isSafeInteger`；label 必须非空 |
| 调用方把 `run` 写成 `async` → unhandled rejection | `runLocal` 检测 thenable 并 catch（语义仍是「已触发」） |
| 对外文档 `docs/api/task-notifications.md` 里「两级分组」那段生成成 `NaN`（`.doc.ts` 单引号未转义，**改动前就存在**） | 转义修好 |
