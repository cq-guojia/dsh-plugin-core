## Background

- 触发原话（2026-11-12，用户）：长耗时弹窗「点了个按钮就开始转圈，但时间比较长」，希望「把所有东西都屏蔽了，但是想留一个按钮……占一行、可以点」，点后「把这个弹窗缩小，推到后面去操作其他东西」，且「该屏蔽的按钮还是得屏蔽；如果他不点这个按钮，其他该不让他关的，还是不让他关」。
- 前两轮已核实的现状（源码级）：`busy` 只让点中的按钮转圈 + 封 ✕ / Esc / 点遮罩三条关闭路径（`src/ui/feedback/Modal.ts:41-44,94-96`；`test/ui.test.mjs:240` 断言「取消钮应保持可点」）；`locked` 才整框锁死（`Modal.ts:45-55,173`、`src/ui/infra/overlay.ts:33-57`），但一刀切、没有例外；Modal 无最小化 / 非模态 / 层级 props（`src/ui/infra/overlay.css:8-11,25-32`）。
- 本轮（2026-11-12）用户把需求扩成三块并追加统一化要求，明确：「在我们讨论完成之前，我明确地说，你不要去动代码」「架构要健壮，不要给我整歪门邪道的东西」「能做就是能做，如果中间实在有坑，直接告诉我啊，不要去强做」「你找这个专家组评估」。用户自己归纳的三块：① 例外按钮；② 跑到后台执行的东西；③ 展示块。

### 需求全文要点（用户原话结构）

1. **例外控件**：允许调用方设置「另外的控件」作为例外，「有可能它不是按钮，有可能是个 input，反正只要是例外，都要把它放出来」；数量与位置不限，`locked` 期间仍可交互。
2. **收起事件**：例外控件里「有一个特殊的事件（比如『收起』）」，点了「我们就会发送到后台去记录一下，然后它就会正常执行，再放到核心的一个统一池子里」；这是「另外的事件」。
3. **事件查看控件（交互）**：「用户可以像使用 button 一样，把这个控件放到某个地方」；控件上显示当前进行中的事件条数；点击展开下拉列表显示正在运行的事件；再次点击收起。
4. **弹窗逻辑**：点列表中的每一条事件「要把那个弹窗给我还回来」；「我不知道那个弹窗是隐藏了还是拉出来重新画，我觉得都可以」。
5. **性能与状态**：「要考虑性能和效率的问题，不能太差，最好是没有什么影响」；「如果它还回来了，就正常在那儿等，再收到下一个」。
6. **结束通知**（用户点名唯一可能麻烦的一处）：「结束是需要用户这边去控制的。怎么个结束方法才能通知到核心，核心才能把这个挪出去？」
7. **统一展示**：A/B/C 都引用本核心时，「每一个收起来的内容，其实都要放到一个统一的地方展示出来」。
8. **分组管理**：默认「直接把项目的名字作为分组名」；「如果项目都叫 A，用户也可以显式地去修改这个分组的名字」。
9. **过滤与显示**：展示控件按项目名过滤 —— (a) 不传 = 全站全显示；(b) 传一个 = 只显示该项目；(c) 传两个 = 显示这两个。
10. **交互形式**：「目前可能只支持弹窗形式，如果能支持其他形式更好，但最少要支持这种弹窗的方式」。

**前一轮已确认的边界**：跨页点开原弹窗不做（用户已接受）；只在当页点开可以（同页 / 未刷新 / 未切页重挂载）；刷新后必点不开。跨页与跨项目**显示纯数据**可以做，不能带组件 / 函数 / ReactNode。

**核实到的宿主事实（源码级，非猜测）**：`docs/design/external/dsh-host.md:214-225` 记官方推送链 —— `dsh-workspace/lib/index.js:526-541` 写口 → `dsh-api-workspace-controller/lib/index.js:54-56` 的 `WorkspaceFeed` 监听 `ctx.on("domain/changed")` → `:115-122` `publish({type:"archived",...})` → `:78-91/:711` 经 `Remote({mode:"stream"})` 的 `follow()` **长连流**下发（**先 baseline 后增量**）→ client `lib/client.js:245-267` 的 `getSnapshot()/subscribe()`。文档原文结论：「官方为归档态提供的正式通道就是『host 领域事件 → follow 流增量 → client 可观察快照 → 订阅』，**没有轮询，也没有独立的归档事件 API**」；本仓 `connectHost` 已订阅同一份 `workspaces.list`，`WorkspaceListStore` 镜像，`SessionViewModal` 用 `useSyncExternalStore` 实时跟随，**零新增连接 / RPC / 定时器**（`:225`）。
⇒ **「事件驱动、不轮询、及时」在宿主体系里是现成的正规做法，不是新发明**。上一轮说的「不能及时」，指的是本仓目前只有请求-响应拉取（`src/ui/infra/host-data.ts:215-220` 的 `fetch`、`src/host/index.ts:36-42` 的 `res.writeHead/end`），任务池自己没有推送通道；不是这套机制不可行。

**core 内部 pub/sub 的现成惯例**：`src/ui/infra/host-data.ts:41-55`（`listeners: Set` + `getSnapshot` + `subscribe` + `update` 通知全体）、`:135-141`（WorkspaceListStore 同款）、`PanelDock.ts:206-210`（`emit`）、`WorkspacePicker.ts:49` / `ModelPicker.ts:80` / `PanelDock.ts:311`（`useSyncExternalStore`）。用户设想的「core 发通知 + 自己监听 + 消费端可选监听」与此同形，**可行**。多插件同页须靠 `src/ui/feedback/toast-host.ts:1-6,12-22` 的 `Symbol.for` 单例去重，否则 N 个副本各发一遍、消费端收到 N 次重复通知。

**数据落点（用户明确禁止文件）**：内存是自然选择且为现有惯例 —— `host-data.ts:38-67` 的 store、`modal-host.ts:19-22` 的 `entries` 全是内存数组；宿主进程重启即失，用户已接受。不放静态文件这条约束不冲突。但有一个后果要记：数据若只放在「某个页面」的内存里，该页面一关数据就没了，其他页面还显示旧状态；「统一的地方」应在所有页面都能读到的那个进程内存里。

**必须一起定 / 核实的坑**：
1. 通知 ≠ 数据：刚打开的页面没听过任何历史通知，必须有一次当前全量状态的 baseline（官方 follow 流也是「先 baseline 后增量」，`dsh-host.md:221`）。这不是轮询，是一次性 / 流首帧；缺了它列表永远空。
2. 参数必须纯数据、可序列化；跨页 / 跨项目传递时不能带函数、组件、ReactNode。
3. 本仓宿主路由面 `HostWebServerLike`（`src/host/index.ts:36-42`）只声明 `writeHead` / `end`，**不支持流式响应**；官方 `Remote({mode:"stream"})` 的 follow 流是官方领域（workspace）专属，`WorkspaceFeed` 只监听 `domain/changed`。**插件能否注册自己的 feed / 长连流，本仓文档与本地 `node_modules/@deepseek-ai/`（目录为空）均无源码级结论**；按 DSH 规则不得凭方法名猜 API，需取与宿主一致版本解包读实现，或由用户给出。这是「跨页及时」唯一未落定的技术前提。
4. 浏览器同源标签页之间另有成熟、零依赖、事件驱动的机制（非轮询），但它不经过宿主进程，数据是各页面内存副本而非「一个总库」，与用户「统一的池」语义不同，且不覆盖跨浏览器 / 跨设备。
5. 消费端「自己去送」时 core 不掌控任务生命周期 ⇒ 容易回到「通知说在跑、没人负责结束」的幽灵条目；通知丢失 / 乱序 / 后台标签页节流期间也要靠 baseline 兜底。
6. 跨项目若 core 版本不一致，共用一份记录无形状校验（`toast-host.ts:15-22` 的 `claim*` 只判 `!== undefined`）。

## Conclusion

- 三块定性（第一轮只读评估，非实现）：① 例外控件 **能做（有条件）** —— `ReactNode` 槽 + 四处豁免，改动集中但不少；② 后台执行 + 统一池 **能做（有条件，坑最多）** —— 跨插件统一必须走 `Symbol.for` 单例而非照抄 `modal-host` 的模块级状态，结束走 `done/fail` 句柄 + settle 兜底；③ 事件查看 + 弹窗还回来 **能做（有条件）** —— 隐藏保树是唯一能保住全部状态的路，但监听与显隐必须联动。
- 不建议强做的一处：现有 `confirmModal` / `alertModal` 的 `Promise<boolean>` / `Promise<void>` 把关闭与结算焊死（`modal-host.ts:128-133,187-192`），「收起退到后台」是第三种生命周期；应先定新契约（建议新开 API，不塞进现有 Promise 签名）。
- 另两处需要明确划界：`skin:'host'` 分支无法承载例外控件与转后台事件；「默认用项目名分组」core 无法自动取，必须由调用方显式传分组名。
- 第二轮定性：跨页 / 跨项目**显示纯数据**能做；跨页**点开**不做（用户已接受）。统一通知（事件驱动、非轮询）可以把「切过去才看见」提升到「变化即达」，宿主已有 `follow` 长连流先例且明写无轮询；但通知必须配 baseline 全量状态，且「插件能否自建长连流」尚无源码级结论，不能先拍板。数据放内存、不放文件，与现有惯例一致。
