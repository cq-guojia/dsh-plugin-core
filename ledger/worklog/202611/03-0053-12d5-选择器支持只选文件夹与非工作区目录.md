## Process

### 一、为什么 picker 只有一个工作区（两层原因，都在核心侧）

1. **清单没人算**：`pickWorkspaceFile` 把 `workspaces` 原样透传（`src/explorer/open.ts:502`），
   demo 调用时没传（`packages/demo/src/sections/blocks.tsx:163-168`）⇒ `FileBrowser` 收到
   `props.workspaces === undefined` ⇒ ▾ 菜单走「只有路径层级」分支（`src/explorer/FileBrowser.ts:199-201`）。
   dock 侧相反：`openFilePreview` 由 `PreviewBody` 自己算 `switchable`（`src/explorer/open.ts:126-138`），
   demo 也显式传了全部工作区名（`blocks.tsx:141`）。
2. **就算传了也切不动**：picker 没有 dock 那层包装，`onSelectWorkspace` 原样透传
   （`src/explorer/open.ts:503`）→ 点别的工作区走 `onPickWorkspace?.()`（`FileBrowser.ts:163-166`），
   无回调即空转；且新工作区的 `sessionId` 没人解析（`list` 必须换会话，见
   `workspaceAnchorForPath` / `anchorSessionForTitle`，`src/explorer/types.ts:566-606`）。

兄弟项目是**在调用方**手写的这套：`pickerWs` 状态 + `workspaceAnchors[pickerWs]` 取会话 + `key` 重挂
（`dsh-task-dispatch-table/src/client/task-editor.tsx:2496-2515`）。核心没接管，所以只有 demo 传什么就有什么。

### 二、后缀过滤 / 只选文件夹（能力已有，缺口是入口）

- `PickFilter { exts, dirs }`（`src/explorer/types.ts:462-465`）+ `matchesFilter`（`types.ts:467-473`）：
  `dirs: true` ⇒ 文件全不匹配（先判 dirs，再判 exts），目录只作导航；已单测（`test/explorer.test.mjs:128-138`）。
- `FileBrowser` 的 `extsOnly` / `dirPickable`（`FileBrowser.ts:592-595`）已保证「扩展名过滤下目录不可选」。
- 缺口：
  - **选不了「当前目录 / 工作区根」**——只有子目录行尾有「选择」钮（`FileBrowser.ts:700-715`），
    想选「就是这个文件夹」没有入口，`dirs: true` 下工作区根本身永远选不到。
  - demo 只有「不限 / 仅 js+md」两个按钮（`blocks.tsx:170-190`），`dirs: true` 没演示。

### 三、能力边界：工作区外目录 / 系统根（官方硬限制）

来源 `docs/design/external/dsh-host.md` §12（解包 `@deepseek-ai/dsh-api-workspace-files@0.2.1-rc.2` 核实）：

- `workspaceFiles.list` 是**会话作用域**：`workspaceRoot` 由 sessionId 派生，`confine` 做
  `contains(root, target)`，为假 ⇒ `workspace-file/outside-workspace`（`lib/index.js:563-583`）。
  ⇒ 向上走到 `..`、或列 `/`、`C:\` 一样被拒。
- `read` / `readBytes` **允许工作区外文件**（`lib/index.js:421 / 480`）——但只认「已知绝对路径」，
  没有目录列举 ⇒ 做不出浏览器。
- `workspaces` 快照只给工作区的 `path` / `title` / `sessionIds`（`dsh-host.md` §11），
  没有「列任意目录」的能力。

结论：**官方 API 内做不到「系统根目录一层层找下去」**，能到的天花板是「宿主已注册的工作区清单」；
再往外只有两条路——① 每个工作区都得绑到一条会话（由宿主决定）；② 插件自建宿主侧 `fs` 路由绕开
fence（`dsh-better-sidebar` 就是这么干的，README 自认「这些路由不做 workspace 包含检查」）。

### 四、如果自建宿主 FS 路由：体积与影响（2026-11-03 追问）

体积（实测基线：`dist` 共 3.3M，其中 JS 1.1M；`dist/host/index.js` 2.7K / 87 行；
`dist/explorer/{types,FileBrowser,open}.js` = 20K + 40K + 24K）：

- 新增量：一条只读 `fs.list` 路由 ≈ 100 行 ≈ 4–6K 未压缩；client 侧 face + 类型 ≈ 100 行 ≈ 3K
  ⇒ 安装体积涨幅 **< 0.5%**，压缩后个位数 KB（explorer 打包产物约 180K 的量级下 ~2–3%）。
- 减量（只在 FS 同时接管 list 时成立）：`RootCache` / `learnRoot` / `absolutizeDir` / `findAnyFileAbs` /
  `relativizeToRoot` / `workspaceAnchorForPath`（`src/explorer/types.ts` 约 200 行）+
  `FileBrowser` 的 `ensureRootLearned` / `rootNonce` / `rootPending`（约 60 行）全部可删
  ⇒ 净体积可能持平或下降。

影响（不是「只补一个能力」）：

| 面 | 变化 |
|---|---|
| 安全边界 | 路由无栅栏 ⇒ 本机任意路径可读；`webServer` 上的本地 HTTP 路由没有鉴权，等于开一个只读磁盘口子 |
| 数据源 | 一旦有了 FS，「工作区内的浏览」也该走它，否则两套路径语义（绝对 vs 工作区相对）永久共存 |
| 预览层 | `read` / `readBytes` / `officeToPdf` 全是会话作用域（`src/explorer/preview/*.ts` ~15 处 `sessionId`）；FS 要接管就全换，officeToPdf 无 FS 等价物，只能保留会话 |
| 选中结果语义 | 现在是工作区相对（`FileBrowser.ts:608-609` 注：绝对路径被宿主 zod 拒过），要改成 `{ absPath, workspaceRel?, workspace? }` |
| 消费方 | 工具 / 附件仍按工作区走 ⇒ 选到工作区外的文件，下游可能用不了（价值取决于消费方） |
| 接线成本 | 消费插件 host `apply` 多一次 `serveXxx(ctx, { path })`，client 要同一个 path 常量 |
| 面包屑 | 绝对路径直接分层（`crumbsOfDir` 已支持 `isAbsoluteish`，`types.ts:477-488`），根 = `/` 或盘符，根名不再靠 anchors 猜 |

### 五、会话到底绑在哪一步（2026-11-03 解包核实，修正第四节的粗判）

解包版本：`@deepseek-ai/dsh-api-workspace-files@0.2.1-rc.5`、`@deepseek-ai/dsh-office-to-pdf@0.2.1-rc.5`、
`@deepseek-ai/dsh-fs@0.2.1-rc.5`（`npm pack` 后读 `lib/*.js`）。

1. **只有 `list` 被栅栏卡住**：`list` 走 `inspect` + `confine`（`workspace-files/lib/index.js:495-505 / 576-583`）；
   `read` / `readBytes` / `stat` 走 `locateFile → inspect`（`index.js:563-574 / 589-605`），`inspect` 只做
   `fs.lstat(path, { cwd: workspaceRoot })`，**不做 contains**（注释原文：「Directory containment is checked
   separately by `list`」）⇒ 相对路径按会话根解析，绝对路径**任意文件都能读**，与会话所属工作区无关。
2. **`officeToPdf` 的会话只用来「授权探针」**：`renderFile` 先 `files.readBytes(scope, path, {range:{0,1}})`
   + `files.stat(scope, path)`，真正的字节是走宿主 `fs` 服务读的（`office-to-pdf/lib/index.js:519-560`，
   `this.ctx.get('fs')`）。因为第 1 条，探针**不会因为文件在工作区外而失败** ⇒ **任意一条有效会话就够，
   不必按路径匹配所属工作区**。
3. **PDF 与 Office 是两回事**：`.pdf` 走 `BytesPreview`（`preview/index.ts:34-43` → `BytesPreview.ts:32`
   的 `readBytes`），**完全不用 `officeToPdf`**；只有 doc/docx/ppt/pptx 走 `OfficePreview`（`index.ts:44-50`）。
   「选了 PDF 读不出来」不成立；读不出来的只有 Office 四类（且是「该能力未就位」）。
4. **宿主有 `fs` 服务**（`ctx.fs`：`resolve` / `lstat` / `stat` / `listDir` / `readBytes` / `contains` /
   `fileUrl` / `processPath`，见 `dsh-fs/lib/types/index.d.ts:94-208`）。若第三方插件宿主半边可注入它，
   自建 FS 路由就是 **~20 行**（`fs.resolve` + `fs.listDir`），且 file URL / version / 编码语义与官方一致；
   不可注入才退回 `node:fs` 自写（~100 行）。
5. ⇒ 「入口不传会话、用到官方能力时再取」**在 FS 接管 `list` 之后成立**，且取会话这一步可退化为
   「随便一条有效会话」，不需要 `workspaceAnchorForPath` 那套匹配（匹配只剩面包屑显示与相对路径解析的用途）。

### 六、树模型（用户 2026-11-03 定的方向）

形态：**单一根**（Linux `/`；Windows 另需「此电脑」+ 盘符）→ 根下先列工作区（别名节点），再列真实目录。
展开规则：文件属于某工作区 ⇒ 在该工作区节点下展开；不属于 ⇒ 从根按真实路径展开（D 盘的文件就在 `D:` 下展开）。

| 点 | 处理 | 状态 |
|---|---|---|
| 工作区节点 vs 真实目录重复 | 同一目录既在「工作区」段又在真实路径下出现 ⇒ 需定「别名是否在真实路径里也显示」 | **待拍板** |
| 嵌套工作区 | 最长前缀赢（`workspaceAnchorForPath` 已有口径，`types.ts:587-606`） | 沿用 |
| Windows 盘符 | `ctx.fs` 无盘符枚举；Linux 只有 `/` | **待拍板**（是否先只支持 Linux 根） |
| 面包屑 | 绝对路径直接分层（`crumbsOfDir` 支持 `isAbsoluteish`，`types.ts:477-488`），工作区节点显示工作区名 | 可行 |
| 排序 / 隐藏项 | 工作区在前、真实目录在后；`.git` / 权限拒绝目录（`/proc`、`/root`）要给错误态不崩 | 待定 |

## Conclusion

讨论结论（2026-11-03，未动代码）：

1. **picker 只有一份工作区**是核心侧的不对称，不是宿主限制：dock 有 `PreviewBody` 算清单 + 换会话，
   picker 把这活留给了调用方。修法 = 给 picker 补同一层包装（约 40 行，复用现有函数）。
2. **只选文件夹 / 后缀过滤能力已有**（`filter.exts` / `filter.dirs`），缺的是「选择当前目录」入口与 demo 演示。
3. **工作区外目录浏览官方 `list` 不支持**：`confine` 卡死；但 `read` / `readBytes` / `stat` / `officeToPdf`
   **只要求一条有效会话，不要求文件在工作区内**（第五节）。⇒ 自建 FS 只需补 `list` 一件事。
4. **会话不前置**：入口不传会话、需要 Office 预览时再懒取一条会话；取不到就只让那一个文件降级提示，
   不影响整个选择器。
5. **树模型**：单一根 + 工作区别名节点，用户已定方向；遗留两个待拍板项（重复目录、Windows 盘符）。
