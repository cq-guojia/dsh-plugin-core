## Background

<!-- What this is for: the words that triggered it / the symptom / a link -->

用户问「我用了 Button 的样式，其他样式会不会也进我的包」。查下来是**全量**：整个 core 只有一个 npm 包 `dsh-plugin-core`（`package.json:3`），`design/ui/utils/explorer/session` 是它的**子路径入口**，不是独立包。样式侧存在一坨全量 blob：

- `src/ui/css.ts:28-46` 把 17 组 CSS 常量（含 explorer / session 的）拼成一个 `CONTROLS_CSS` 字符串；
- `src/ui/css.ts:66-69` 的 `ensureControls()` 一次性把整坨灌进 DOM；
- 全体 ui / explorer / session 组件渲染时都调它（src 下 60 处调用点）。

后果分两层，**两者行为相反**：

- **控件代码**能按需：`package.json:20` 有 `sideEffects:false`，tree-shaking 能删掉没用到的控件模块（`FileBrowser` / `explorer/preview/*` / `CodeViewer` 等在各自子路径，不引就不打包）。
- **CSS 不能按需**：`Button → css.ts → CONTROLS_CSS → 全部 17 组`，因为 `css.ts` 静态 import 了所有 CSS 模块。这一步让摇树彻底失效——不管消费端怎么引，写一个组件就背上全部 CSS 文本。

目标：把「CSS 也变成按需」，让 `Button` 的图里只含 `BUTTON_CSS`。

## Process

<!-- Pitfalls and evidence: with revision + file:line or symbol names -->

**收益前置验证（实测）**：改造能不能省包体取决于消费方，所以在动手前先验了三件事，全部通过 ——

1. **消费方写法是具名的**（前提成立）：本机 `/code/dsh-plugins/` 下三个插件里，只有 `dsh-task-ledger` 引了 core，四处 import 全是具名（`packages/plugin/src/client/index.ts:12-13`、`rows.ts:11`、`board-home.ts:27`），**没有 `import * as`、没有 `require`** ⇒ 摇树前提具备。
   （`dsh-task-dispatch-table` / `dsh-session-title-pattern` 本机尚未引 core，无法核验；将来它们接进来时按同样口径再验一遍。）
2. **现状确实全量**（命门证实）：esbuild（`platform=browser`、`bundle`、`minify`，与 demo 构建 `packages/demo/build.mjs:62-80` 同一套参数）打「只 `import { Button }`」的最小入口 ⇒ 产物 **150.6 KB**，17 组 CSS **全部在包里**（可探测的 16 组全命中，`HINT_CSS` 因类名与 `FIELD_CSS` 重叠没有唯一点探针，但同在引用链里）。只用 Button 却背了 `CARD` / `PANEL_DOCK` / `EXPLORER` / `SESSION` / `CODE_VIEWER` 全部样式。
3. **摇树能力存在**（对照实验）：入口只 `import { BUTTON_CSS }`（绕过 `css.ts` 聚合）⇒ 产物 **14.2 KB**，同文件的其余 6 组 CSS **全部被摇掉**。说明「CSS 作为被显式引用的字符串常量」这条路能被 esbuild 正常摇除 —— 反过来印证 webpack 官方那条：若改成副作用式 `import './x.css'` 就会被 `sideEffects:false` 连样式摇掉；我们这种写法既不会被误删、又能按需摇除，两头都对。

**体积账**：17 组 CSS 合计 **71.7 KB**；只用 Button 只需 `BUTTON_CSS` 的 **9.4 KB**；可省 **62.3 KB（≈87%）**。以「只用 Button」的消费方算，产物从 150.6 KB 量级降到约 90 KB 量级。⇒ **收益真实且可观，值得做。**

**机制已就位，不用新建东西**：`src/design/style-kit.ts:78-83` 的 `registerStyle` 自带幂等（`if (domains.get(domain) === css) return`），`applyStyle` 便是 per-domain（`:99-102`），且全库只有一个 `<style id>`（`:62-72`）——每组件 render 时调一次自注入是安全的。

**真正的命门**：必须是 `css.ts` **不再静态 import** 全部 CSS 常量。只改注入方式、保留 `CONTROLS_CSS` 聚合，包体一个字节都不会少。

**顺序（本轮实测的结论）**：现在 `CONTROLS_CSS` 是固定数组顺序，`css.ts:27` 注释明写「同特异性规则后注入者胜出」。改成自注入后，顺序会变成**首次渲染顺序**。仅在「两个常量定义了同特异性同名选择器但规则不同」时才会翻车——表现为同一个控件从不同路径进入外观不同，偶发且难查。
实测扫了 324 个真实类名，同名的是 6 个：`dshpc-iconbtn`、`dshpc-hint`、`dshpc-seg`、`dshpc-seg--bordered`、`dshpc-picker`、`dshpc-picker__trigger`。逐条比对规则，**6 个全部是「高特异性上下文版本」**（`.dshpc-split .dshpc-seg` / `.dshpc-num .dshpc-iconbtn` / `.dshpc-fieldwrap--block > .dshpc-hint` 等），特异性都高于单类规则，**顺序无关 ⇒ 当前不会出视觉问题**。
但这属于「现状侥幸」而非机制保证。查过官方口径后，**不再采用「固定排序」这条路**，改用「禁止依赖顺序」（见下节）。

**业界方案对照（本轮查的一手文档）**

| 议题 | 权威来源 | 结论对本项目的影响 |
|---|---|---|
| 是否该依赖样式出现顺序 | Emotion 官方 Composition（https://emotion.sh/docs/composition） | 官方原话：「the order that they're defined is the order they'll be applied. This can lead to hacks with `!important`」；正解是组合（composition），「you don't have to think about the order that styles were created」。⇒ **依赖顺序本身就是被官方否定的做法**，管住「不许出现需靠顺序才能对的规则」才是正道，固定排序只是止痛剂 |
| 跨来源 / 跨层的顺序 | MDN @layer（https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@layer，属 CSS Cascading and Inheritance L5，Baseline 自 2022-03 widely available） | 「once the layer order has been established, **specificity and order of appearance are ignored**」；且「Having declared your layer names … you can add CSS rules to the layer by re-declaring the name … the layer order will not be changed」。⇒ @layer 能彻底消除「何时注入」对跨层优先级的影响。**但代价是层间忽略特异性**，所以「一个组件一层」会直接打掉现有 `.dshpc-split .dshpc-seg` 这类靠高特异性生效的定制 ⇒ 只适合做**跨来源**分层（tokens / dshpc 整体 / 消费方 override），**不适合按组件拆层** |
| 按需打包的前提与坑 | webpack 官方 Tree Shaking（https://webpack.js.org/guides/tree-shaking/） | `sideEffects` 的含义：「If no direct export from a module flagged with no-sideEffects is used, the bundler can skip evaluating the module」。官方点名的事故 "Real-World Impact #1: **CSS not being included: Components render without styles**" —— 例子是组件里 `import "./Button.css"` 这种**副作用式** CSS 导入，在 `sideEffects: false` 下会被连同样式一起摇掉；Pitfall #1「Over-optimistic sideEffects: false」把 CSS imports 列为头号隐藏副作用。⇒ **我们这套「CSS 是 TS 里 `export const X_CSS` 的字符串常量、被显式引用」的写法恰好安全**：它是被使用的值，不是副作用 import。**反面警告：本项目绝不能退回 `import './x.css'` 那套**（宿主跑 CJS 闭包、内核不加载 css 资源，本来也走不通，见 AGENTS.md） |
| （社区佐证，非权威）运行时 CSS-in-JS 的顺序 | Workday canvas-kit 讨论「Emotion cannot predict style insertion order」（https://gitgub.com/Workday/canvas-kit/discussions/2893） | 第三方组件库同样承认运行时 CSS-in-JS 的插入顺序不可预测，与上表 Emotion 官方口径互相印证 |

**结论**：本方案（每组件自带自己的 CSS 常量 → 运行时 register 到单一 `<style>`）与业界通行做法一致；要守的规矩是**不依赖顺序**（用更高特异性或组合来表达定制，当前 6 个重名正是这么写的），而不是去固定注入顺序。

**token / 颜色链安全（实测）**：17 个 CSS 常量里**没有任何一个**引用别的常量定义的变量，只有三类来源——design token（132 个，tokens 域始终注册且 `style-kit.ts:50` 的 sort 强制排最前）、本文件私有变量（`--btn-bg` 等）、7 个由组件 JS 运行时发布的变量（`--dshpc-page-inset-right`、`--dshpc-mq-dur` / `-dist`、`--dshpc-dock-gap` / `-h`、`--ds-font-family-code`）。拆分不影响这条链。

**交叉引用清单（实测，比预想轻）**：用「抽 CSS 里真实定义的类名 → 反向映射每个组件用到的类属于哪份 CSS」的办法扫了 98 个源码文件，真正需要同时注入多份的**只有 4 个文件**（见 To Do）。其余全是干净 1:1。`Segmented` / `Picker` 用到的 `SPLIT_GROUP_CSS` 部分不用管——那是 `SplitGroup` 组件自己的份内事（`.dshpc-split` 祖先只有它才产生）。

**顺带发现（与本次拆分无关，建议单独看）**：源码里有若干「用到但 CSS 里查无此定义」的类名，如 `dshpc-checkbox`、`dshpc-main`、`dshpc-root`、`dshpc-modal-host`、`dshpc-space-2` 等；部分是 token 变量名误判、部分是运行时容器钩子，但 `Checkbox` 若本该有自绘皮肤却是另一回事。
