## Background

<!-- What this is for: the words that triggered it / the symptom / a link -->

用户问「我用了 Button 的样式，其他样式会不会也进我的包」。查下来是**全量**：整个 core 只有一个 npm 包 `dsh-plugin-core`（`package.json:3`），`design/ui/utils/explorer/session` 是它的**子路径入口**，不是独立包。样式侧存在一坨全量 blob：

- `src/ui/css.ts:28-46` 把 17 组 CSS 常量（含 explorer / session 的）拼成一个 `CONTROLS_CSS` 字符串；
- `src/ui/css.ts:66-69` 的 `ensureControls()` 一次性把整坨灌进 DOM；
- 全体 ui / explorer / session 组件渲染时都调它（src 下 60 处调用点）。

后果分两层，**两者行为相反**：

- **控件代码**能按需：`package.json:20` 有 `sideEffects:false`，tree-shaking 能删掉没用到的控件模块（`FileBrowser` / `explorer/preview/*` / `CodeViewer` 等在各自子路径，不引就不打包）。
- **CSS 不能按需**：`Button → css.ts → CONTROLS_CSS → 全部 17 组`，因为 `css.ts` 静态 import 了所有 CSS 模块。这一步让摇树彻底失效——不管消费端怎么引，写一个组件就背上全部 CSS 文本。

目标：把「CSS 也变成按需」，让 `Button` 的图里只含 `BUTTON_CSS`。

## Process

<!-- Pitfalls and evidence: with revision + file:line or symbol names -->

**机制已就位，不用新建东西**：`src/design/style-kit.ts:78-83` 的 `registerStyle` 自带幂等（`if (domains.get(domain) === css) return`），`applyStyle` 便是 per-domain（`:99-102`），且全库只有一个 `<style id>`（`:62-72`）——每组件 render 时调一次自注入是安全的。

**真正的命门**：必须是 `css.ts` **不再静态 import** 全部 CSS 常量。只改注入方式、保留 `CONTROLS_CSS` 聚合，包体一个字节都不会少。

**顺序（本轮实测的结论）**：现在 `CONTROLS_CSS` 是固定数组顺序，`css.ts:27` 注释明写「同特异性规则后注入者胜出」。改成自注入后，顺序会变成**首次渲染顺序**。仅在「两个常量定义了同特异性同名选择器但规则不同」时才会翻车——表现为同一个控件从不同路径进入外观不同，偶发且难查。
实测扫了 324 个真实类名，同名的是 6 个：`dshpc-iconbtn`、`dshpc-hint`、`dshpc-seg`、`dshpc-seg--bordered`、`dshpc-picker`、`dshpc-picker__trigger`。逐条比对规则，**6 个全部是「高特异性上下文版本」**（`.dshpc-split .dshpc-seg` / `.dshpc-num .dshpc-iconbtn` / `.dshpc-fieldwrap--block > .dshpc-hint` 等），特异性都高于单类规则，**顺序无关 ⇒ 当前不会出视觉问题**。
但这属于「现状侥幸」而非机制保证，所以 To Do 里仍把确定性排序闸列为第一项：几乎零成本，一次性抹掉整类隐患。

**token / 颜色链安全（实测）**：17 个 CSS 常量里**没有任何一个**引用别的常量定义的变量，只有三类来源——design token（132 个，tokens 域始终注册且 `style-kit.ts:50` 的 sort 强制排最前）、本文件私有变量（`--btn-bg` 等）、7 个由组件 JS 运行时发布的变量（`--dshpc-page-inset-right`、`--dshpc-mq-dur` / `-dist`、`--dshpc-dock-gap` / `-h`、`--ds-font-family-code`）。拆分不影响这条链。

**交叉引用清单（实测，比预想轻）**：用「抽 CSS 里真实定义的类名 → 反向映射每个组件用到的类属于哪份 CSS」的办法扫了 98 个源码文件，真正需要同时注入多份的**只有 4 个文件**（见 To Do）。其余全是干净 1:1。`Segmented` / `Picker` 用到的 `SPLIT_GROUP_CSS` 部分不用管——那是 `SplitGroup` 组件自己的份内事（`.dshpc-split` 祖先只有它才产生）。

**顺带发现（与本次拆分无关，建议单独看）**：源码里有若干「用到但 CSS 里查无此定义」的类名，如 `dshpc-checkbox`、`dshpc-main`、`dshpc-root`、`dshpc-modal-host`、`dshpc-space-2` 等；部分是 token 变量名误判、部分是运行时容器钩子，但 `Checkbox` 若本该有自绘皮肤却是另一回事。
