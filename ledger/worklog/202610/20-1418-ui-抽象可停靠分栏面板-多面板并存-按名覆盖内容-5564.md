- **宿主右栏是另一条路，且对整页面板插件不可用**：`ctx.sidebarRight.openResource` 走「当前挂载 seat」，插件整页面板激活即顶替会话区 ⇒ 无 seat ⇒ 调用即报错（`dsh-task-dispatch-table/docs/design/external/dsh-capabilities.md:50`，源项目决策 39 已因此排除）。宿主也未导出任何 `SplitPane`/`Drawer` 组件，分栏是 `dsh-client-ui-layout` 内部实现。
- **用户 2026-10-20 补充的核心诉求**：身份策略要**按项目（id）单独配**，不是一个 dock 一把开关。原话例子：同一串 ABCC，`C` 若配「唯一」则只有 A B C；`C` 若配「可多份」则是 4 个面板、两个 C。⇒ 面板模型不能只有 `open(id)` 覆盖语义，必须带 `mode`。
- **上限口径澄清**：`maxPanels` 是**调用方的数**，库不猜。用户原话「他设置两个就是两个，设置三个就是三个」，默认 3、超限拒绝新开，写文档说明即可。
- **还讨论了两种「不拒绝」的出路**：① `overflow: 'evict'`（满了自动关最久未激活的腾位，用户说的「自动」参数）；② `layout: 'tabs'`（单列 + 顶部切换条，不限宽度，超额按保活数淘汰）。两者都能满足「不停开」，但都改 API 形态，**待用户确认是否同批做**。
- **「浮动」方案不推荐**：浮层不占布局 ⇒ 挤不窄正文，只会盖住内容，与源项目 2026-09-28 明确要求的「分栏压过来、不是盖上去」相反（`archive-session-css.ts:22-24` 的注释与真机修复记录）。
- **2026-10-20 追问「能不能不限上限（开 10~20 个）」**：可以，但**只在单列切换形态（tabs）下成立**；并排形态下宽度是物理约束，`limit` 删不掉。⇒ 结论定为**双闸模型**：数量闸（`limit`，开发者参数，可传 `undefined` = 不限）+ 宽度闸（主区保底宽，先到者生效）。并排默认 3；tabs 不传 limit 即不限。
- **`overflow: 'evict'` 判定为不必要**：它解决的是「上限到了还想开」，而 tabs 形态本身没有宽度压力，用户自己关即可；保留它只会让语义变多。仅在并排形态保留 `reject`（默认）与 `evict` 两档可选。
- **不限上限的隐藏成本**：tab 条在十几个标签时要能横向滚动/收纳；面板内部可能挂 CodeMirror / iframe / 轮询，20 个同时保活是真实内存风险 ⇒ 不限是「允许」，不是「推荐」，文档要写清。

## 结论

**功能可实现，无技术硬伤。** 「多面板并存 + 按名覆盖」本质是一个 keyed 注册表 + N 个 flex 成员列，难点在工程量与多实例改造，不在可行性。

三条支撑：

1. 壳与内容已分离，抽象面只有 `translate` / token / 持久化 key 三处注入；
2. 需要打破的 8 个单例点全是具名、可枚举的局部改动，无架构级阻塞；
3. 宽度上限、拖拽性能、iframe 吞指针、弹窗让位这四个已知坑在源项目都已有落地方案，可照搬。

**定稿的面板模型**：`open({ id, title, content, mode })`，`mode` 是**该 id 的固有属性**（首次 open 决定，后续冲突只告警不切换）；`single` 命中即原槽位换内容、`multi` 命中即追加实例（实例键 `id#n`，各自可关）。上限与超限行为是 dock 级参数（`limit` + `overflow`），与 id 级 `mode` 正交，两者组合覆盖 ABCC 的两种结果。

两条边界（属设计约束，不属硬伤）：

1. 分栏**必须由调用方放进自己的 flex 布局**，不能像 `Modal` 那样自挂 `document.body`（自挂只能遮盖、挤不窄）；
2. 「贴着宿主聊天正文的右栏」是宿主 `sidebarRight` 的地盘，**整页替换会话区的插件用不了**，本任务不做。
