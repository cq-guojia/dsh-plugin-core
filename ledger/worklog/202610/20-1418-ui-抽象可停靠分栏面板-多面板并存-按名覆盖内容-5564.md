## 结论

**功能可实现，无技术硬伤。** 「多面板并存 + 按名覆盖」本质是一个 keyed 注册表 + N 个 flex 成员列，难点在工程量与多实例改造，不在可行性。

三条支撑：

1. 壳与内容已分离，抽象面只有 `translate` / token / 持久化 key 三处注入；
2. 需要打破的 8 个单例点全是具名、可枚举的局部改动，无架构级阻塞；
3. 宽度上限、拖拽性能、iframe 吞指针、弹窗让位这四个已知坑在源项目都已有落地方案，可照搬。

**定稿的面板模型（用户 2026-10-20 最终口径）**：

- `open(id?, { title, content })`：**组名 = 窗口，一对一**。不传 id = 默认窗口（保留名 `default`）；传 id 就开那一组。
- 该 id 已开 ⇒ **原位覆盖内容**（槽位、顺序、宽度都不变，不新增一栏）。
- 该 id 未开 ⇒ 新增一右栏；**已满 3 栏 ⇒ 拒绝**，不静默丢弃，返回失败结果供调用方提示/报错。
- 关掉任意一栏（如 default）后再开新组名（如 C）⇒ 允许，占用腾出的位置。
- 无 tabs、无 tab 条、无自动淘汰：**面板内部的标签切换是消费方自己的事**。
- 上限是 dock 参数，默认 3，调用方可设；宽度上另有一道物理闸（主区保底宽），先到者生效。

两条边界（属设计约束，不属硬伤）：

1. 分栏**必须由调用方放进自己的 flex 布局**，不能像 `Modal` 那样自挂 `document.body`（自挂只能遮盖、挤不窄）；
2. 「贴着宿主聊天正文的右栏」是宿主 `sidebarRight` 的地盘，**整页替换会话区的插件用不了**，本任务不做。
