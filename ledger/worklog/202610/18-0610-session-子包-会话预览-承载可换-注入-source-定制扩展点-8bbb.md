## 过程

**定位**：`session` 是「有实质内容、会持续长大的功能模块」，所以配独立成包（立包判据 §4）；
而 `Modal` 只是呈现形式，留在 ui（用户拍板）。

**契约**（需求文档 §6）：`SessionPreview({ sessionId, source, variant })`。

- `source` 是**取数能力接口**（`listMessages` + 可选 `download`），不是静态数据 ——
  会话预览**内部有交互**（附件下载 / 打开文件），光有消息流不够。
- `variant: 'modal' | 'sidebar' | 'page'` —— 承载可换是用户明确要求；modal 走 ui 的 `Modal`。
- **定制扩展点**：`renderMessage` 可完全接管单条消息渲染（富内容 / 工具卡走这里）。
- 加载 / 失败（带重试）/ 空态三态齐备，文案走内置字典。

**⚠ 本任务没做的事（必须说明）**：

用户要的是「把 dispatch 里写好的会话预览**整体**封装」。本任务**只建了契约与承载骨架**，
**没有搬运 `dsh-task-dispatch-table/src/client/mirror/` 的那 15 个文件**
（ChatView / MessageItem / GenericCommandCard / TurnProcessNodeView / StatDialog …）。
那些文件是**逐行镜像官方 ui-tool** 的实现，依赖官方 CSS 类名与宿主消息格式，
搬运 + 让它在没有官方包的环境下编译，是一个需要单独验证的大工程。
⇒ 本版默认渲染只做「角色 + 纯文本 + 附件」，富内容靠 `renderMessage` 扩展点接。

理由记在这里，避免明天看到「会话预览」以为已经全好了：
**它现在能跑通契约与三种承载，但长得不像官方会话。**

## 结论

`dsh-plugin-core/session` 骨架可用：三种承载 + 注入 source + 定制扩展点 + 三态，
27 条自检全过，入口可 import。

留坑：
- 会话渲染**只有最简版**，官方会话那套镜像（工具卡 / 代码块 / 推理行等）**未搬** —— 后续任务。
- 没做消息分页 / 增量加载（长会话会一次全渲染）。
- 仍未在浏览器渲染验证。
