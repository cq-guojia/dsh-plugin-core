## 背景

用户 2026-10-21 提问：多个插件都引 `dsh-plugin-core`，同时弹 toast 会怎样？
结论是**真问题**：core 会被打进每个插件的 bundle，每个副本各有一份
`src/ui/Toast.ts` 的模块级状态（`root` / `currentPosition` / `themeObserver`），
`ensureToaster()`（`src/ui/Toast.ts:75-88`）挂容器时**连 `getElementById` 都不查**，
直接 `createElement` + `id = 'dshpc-toast-root'` + appendChild。
⇒ N 个插件同页 = body 上 N 个**同 id** 的 div（重复 DOM id）+ N 个 React root + N 个
Toaster；三家同时弹且 position 相同 = **N 个提示区叠在同一块屏幕位置**。
用户原话确认理解：「一旦多个插件用，大家一块弹就疯了」。
用户要求：不只用官方 toast；至少「引用本框架的插件」（ABC 多少家）之间要有统一方案。

**已拍板的方案（用户 2026-10-21 确认）**：在 `globalThis` 上用 `Symbol.for` 办一个
跨副本单例 toast 宿主——第一个到场的副本挂唯一容器 + 唯一 Toaster，并暴露
`show()` 命令式入口；之后所有副本（含跨版本）都把提示交给已注册的宿主渲染。

## 给执行者的实现规格（用户已拍板的细节，照做即可）

### 1. 为什么必须共享「命令式入口」而不是「React root」

sonner 的 `toast()` / `toast.custom()` 是**模块级 store**：B 副本调自己 bundle 里那份
sonner，事件只进 B 的 store，A 副本的 Toaster 收不到。所以宿主暴露
`show(payload)`，由先到者用它**自己 bundle 里**的 sonner 执行，不能共享 root。

### 2. 单例写法

```ts
export const TOAST_HOST_KEY = Symbol.for('dsh-plugin-core/toast-host')

export function claimToastHost<T>(create: () => T): T {
  const g = globalThis as typeof globalThis & { [TOAST_HOST_KEY]?: T }
  g[TOAST_HOST_KEY] ??= create()
  return g[TOAST_HOST_KEY] as T
}
```

`Symbol.for` 的注册表是全局的，跨 bundle 副本天然共享同一个符号 ⇒ ABC 三个插件
（哪怕 core 版本不同）自动归并到一个宿主。无 `document` 的环境（Node 单测 / SSR）
由 `Toast.ts` 侧静默跳过，不注册。

### 3. 宿主接口

```ts
export interface ToastPayload {
  message: string
  variant: ToastVariant        // info / success / error / warning
  style: 'native' | 'card'     // native = showToast（sonner 原味）；card = notify（我们的卡）
  description?: string
  durationMs: number
  color?: string               // showToast 的整条自定义色
  onDismiss?: () => void
  actions?: ToastAction[]      // notify 的右侧按钮（1–2 个）
}

export interface ToastHost {
  show(payload: ToastPayload): void
  setPosition(position: ToastPosition): void   // 全局统一位置
}
```

### 4. 三条取舍（用户 2026-10-21 已明确接受，不要自行"优化"）

| 取舍 | 内容 |
|---|---|
| 样式由第一个副本决定 | A 用 core 0.2.14、B 用 0.3.0 时，提示外观是**先加载那一份**的。要消除靠版本治理（各插件同步升 core），不做技术处理 |
| position 全局共享 | 任一插件 `setPosition` 对所有插件生效。一个屏幕一个区，这是「统一」的必然代价 |
| 不做卸载回收 / 引用计数 | 停用插件只留一个不可见空 div + 一个对象引用；DSH 装插件本就要重启核心，页面刷新即重置。**引用计数解决不了唯一风险场景（见下），故不加** |

### 5. 已知风险（用户已知并接受，不要加自愈）

热替换（HMR）场景：注册宿主的副本被废、宿主容器被移出文档时，其他插件的 toast
会渲染到不可见位置。触发条件窄（要宿主真的清 DOM），用户明确选择不加
`isConnected` 自愈。若用户后续改主意，再加的就是「show 前检查 `container.isConnected`，
掉了重建」5 行，不动整体结构。

### 6. 兼容性要求

- `showToast` / `notify` / `showHostToast` 的签名与行为**完全不变**（demo 的
  FeedbackPage 在用，不要改调用方）。
- `src/ui/index.ts` 的导出不变（`toast-host.ts` 是内部模块，无需导出；
  若需导出，加进 `src/ui/index.ts` 并在 PR 说明里写）。
