## 过程

### 一、继承老任务的调研结论（2026-10-18 已裁决，需求文档直接引用不重新论证）

**打包硬约束**（源自 dispatch 表 README:115、tsdown.client.config.ts:19-58、src/client/ui/style.ts:1-27）：

- 宿主以 git/npm 装插件**不跑构建脚本** ⇒ 包必须发预编译 dist，不能指望消费方 build。
- client 产物是 `window.__ModuleLoader__.load({ id, factory })` 的 CJS 闭包，`import './x.css'`
  只会产出独立 css 资源、**内核不加载** ⇒ 样式只能以 TS 字符串 + 运行时注入分发。
- `react` / react-dom / `@deepseek-ai/*` primitives 走 PLATFORM_MODULES 白名单保留 `require()`；
  打进包里会产生第二份 React 实例（hooks 直接崩）⇒ 一律 optional peer + external。

**注入器工厂化（硬约束，非选项）**：现 `src/client/ui/style.ts:28,34` 是模块级单例 + 固定 style id
`dsh-task-dispatch-table-ui`，多插件同页必然互相覆盖 ⇒ 必须改成 `createStyleKit({ id, prefix })`，
style id 带插件前缀，token 前缀参数化。

**包形态裁决**：`dsh-plugin-core` 一个 npm 包 + 子路径导出（`./ui`、`./files`，重入口 `./files/codemirror`）。
曾考虑拆多包，结论是 tree-shaking 让拆包在产物大小上零收益，只多出双 tag / 发布顺序 / 跨包 peer 区间
的协调成本；规模变大到依赖区间互相打架、或 files 因宿主 API 频繁 breaking 时再拆（files 是头号候选）。
用户确认的模型：**安装 = 整包；使用 = 按子路径 tree-shaking**。

**边界（四方调研共识）**：

- 进：token 映射表（前缀参数化）、注入器工厂、基础控件（Segmented / Button / Input 家族 / Textarea /
  Checkbox / MarqueeText / Loading / SectionHead / BackToTop / LiveText / resizer）、日期时间、
  文件浏览、HTTP client 骨架、i18n 基建、宿主类型面 + 能力探测、官方 CSS-module 类名发现。
- 不进：`mirror/` 官方会话 UI 全家（`ui-style-guide.md:108,110` 已判定「不抽」，宿主升级三插件集体漂移）、
  业务 token（`--tdt-cal-*` / chip-bg / filechip / PROCESS_FILES_CSS）、TaskPicker、CodeViewer 审美、
  `PANEL_CONTENT_ID` 页面几何、任何插件私有路由 / DB 表、`@deepseek-ai/*` 运行时依赖。

**发布方式**：npm 公开包。私有包会让最终用户装插件时要配 token（GitHub Packages 上次就是因此被否），
且 npm 私有需付费；**公开 ≠ 开源**——发布物只是 `files` 指定的 dist，源码仓可以私有。OIDC 发布复刻现有
三个仓的 workflow 即可。包名 `dsh-plugin-core` 2026-10-18 探为空闲，**发布前再 `npm view` 复核一次**。
备选 `dsh-plugin-koc-core` 留作后备。

### 三、问题清单的利弊与推荐

**问题 1：日期等公用方法放 `./utils` 还是并入 `./ui`**

- 独立 `./utils`
  - 好：ui 只管样式与控件，职责清；纯函数无 DOM 依赖，**host 侧（node）也能引**（dispatch 的
    `schedule-next.ts` / `tasks.ts` 就有日期逻辑）；tree-shaking 干净；以后塞字符串 / URL / 防抖不污染 ui。
  - 坏：多一个子路径要记；日期格式化跟 DateTime 控件强耦合（时间文案、相对时间、时区），
    改控件可能要跨两个子包；多一个入口多一份类型声明要维护。
- 并入 `./ui`（README 现状）
  - 好：日期方法基本只被 DateTime / time-text 这类 UI 用，跟着控件走改一处；心智简单；少一个入口。
  - 坏：host 侧想用就得引 ui，可能带进样式注入副作用与 DOM 代码；纯函数与 UI 耦合，
    以后加非 UI 的工具函数会越来越勉强。
- **推荐**：独立 `./utils`。判据用「能不能在 node 里跑」切分——纯日期计算（parse / format / 时区 / 区间运算）
  进 utils；跟渲染绑死的「时间文案 / 相对时间」留在 ui，跟 DateTime 一起改。
  前提是先补调研：host 侧是否真的要用（见待办 C）。

**问题 2：文件浏览现在抽不抽、叫什么**

- 列 v2，v1 只做 ui
  - 好：抽象有第二家校准后再定型，不会「把一家的形状当通用」；v1 先用**真实重复**（样式 + 日期）
    跑通整包链路（tsdown 出 dist → npm 发版 → 消费者接入），链路通了再加子包成本很低。
  - 坏：用户做新插件时「文件浏览还是要抄」这个原始痛点短期不解决；第二家什么时候出现不确定。
- 现在就抽，标注「单一来源、未经第二家验证」
  - 好：痛点立即解决，dispatch 先删自有副本，立刻形成第二个「消费者—供给方」闭环。
  - 坏：抽象大概率 v2 要推翻重来；`process-files.tsx` / `task-file-context.tsx` 明显带业务
    （`PROCESS_FILES_CSS` 已被判「不进」），切分线现在就得划，容易划错；host 侧文件 API 若 breaking，
    包要跟着发 major。
- **推荐**：列 v2，但现在把 `file-browser.tsx` 依赖的宿主 API 面写成调研结论（见待办 C），
  v2 开工时直接用；package.json 里先**不要**留空 `./files` 导出，避免空承诺。
- 命名：`./files` vs `./finder`
  - `./files`：名词复数，覆盖浏览 + 预览 + 选择，跟 `ui` / `utils` 同风格，以后塞预览不别扭。
  - `./finder`：macOS 比喻形象，但英文里易与「查找 / 搜索」混淆（通用叫法是 file browser），
    且以后真要加「搜索文件」会语义打架。
  - **推荐** `./files`；重入口建议 `./files/preview`（老文档写的 `./files/codemirror` 是预览的实现细节，
    不该暴露在入口名里）。

**问题 3：统一 token 后审美以谁为准**

- 以 dispatch 为准（控件最全、第一个消费者）
  - 好：现成 17KB token + 26KB 控件 CSS 直接搬；dispatch 自己不改视觉，改造风险最小。
  - 坏：ledger / stp 接入后视觉会变（输入框高度 / 层级），肉眼可见；等于把一家审美强加给另两家。
- 只对齐 token 名、数值可覆盖（包给默认值 = dispatch）
  - 好：接入不强制视觉变更，阻力小；分叉先被记录而不是被消灭。
  - 坏：默认值 + 覆盖 = 两套真相长期并存，「不标准」这个原始痛点只解决一半。
- **推荐**：以 dispatch 为准为主，但把高度 / 圆角这类易争议的给覆盖参数；接入后跑视觉对比，
  再决定哪些默认值要改。**需要用户拍板：能不能接受另两家视觉微调。**

**问题 4：v1 做多大 / 分期**

- 建议：v1 = `./ui`（token 前缀参数化 + 注入器工厂 + 基础控件 + 日期按问题 1 的结论归位）；
  v2 = `./files`；v3 = HTTP client 骨架 / i18n 基建 / 宿主类型面 + 能力探测 / 官方类名发现。
- **一个子包一个任务**，需求文档只给分期与每期的验收口径，不再出现「一个任务做完 v1.0」。

**问题 5：首批消费者与验收口径**

- 老文档定的前两个消费者：dispatch（删自有副本）、ledger（删 `tokens.ts` / `ui.ts`）。
- 建议的验收口径：两家接入后，控件视觉与接入前**逐一截图对比**，差异要么被接受要么回滚；
  包发 dist、消费者不跑构建（复现硬约束）；`npm view` 复核包名。
- 待定：ledger 是 pnpm workspace 多包结构，接入走 npm 装还是 workspace link，要不要现在定。

**问题 6：需求文档落盘在哪**

- 台账（`ledger/`）只装状态与链接，成果不进台账。
- 建议 `docs/requirements.md`（README.md 是对外说明，需求文档是内部规格），README 挂一行指向它。
- 备选 `REQUIREMENTS.md` 放仓根（跟 README 平级，一眼可见）。
