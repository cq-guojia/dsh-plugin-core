## 背景

用户原话要点：同级三个 DSH 插件（dsh-task-dispatch-table / dsh-session-title-pattern / dsh-task-ledger）
里，下拉框 / 搜索框 / 滑轨样式、日期选择、右边文件浏览被反复抄写；每做新插件都要对 agent 说
「去抄这个项目的样式」「把右边文件浏览抄一份过来」。两个问题：一是麻烦，二是**不标准、不知道抄得怎么样**。
诉求：提炼成自己开发 DSH 用的包，放 GitHub / NPM，以后插件按文档 npm 引用，不自己写。

**为什么另起本任务**：原任务 `20261018-0048-dsh-插件共享底座-样式-通用功能-7ade` 建错了——它一个 doing
任务吞下「调研 + 建包 + 发版 + 三家消费者改造」整件事，worklog 里既有打包约束/边界/发布方式的调研结论，
「下一步」又直接跳到「搬 tokens.ts + 改注入器工厂 + 配 tsdown」，等于一个任务覆盖 v1.0 全部实现。
那不是任务粒度，是项目粒度（2026-10-18 老任务已按用户指令删除，其调研结论全文迁入本文件「过程」节）。

**本任务的边界**：只做需求澄清 + 产出需求文档。**不写实现代码、不搬任何 ts 文件、不配构建。**
需求文档定稿后，每个子包各自另建任务。

**⚠ 服务对象（2026-10-18 用户纠正前提，最重要的一条）**：这个包**不是**为了消灭现有三家的重复，
它服务的是**以后要写的每一个 DSH 插件**。现有三家只是（a）需求会反复出现的**证据**，
（b）第一批消费者。⇒ 判据不能是「三家都抄了什么」，必须是「任何一个 DSH 插件大概率都要用到什么」。
三家没有、但未来插件一定会用到的东西，照样该进；三家都有、但属于业务的东西，照样不进。

**由此确立的多语言原则**（同日用户拍板，见 Q2）：核心提供什么，核心就负责它的多语言——
包内控件自带的提示 / 错误文案由包自己处理多语言；**插件自己界面的文案由插件自己管，包不接管**。
不是要在一个包里解决所有插件的提示词多语言。

## 过程

### 一、继承老任务的调研结论（2026-10-18 已裁决，需求文档直接引用不重新论证）

**打包硬约束**（源自 dispatch 表 README:115、tsdown.client.config.ts:19-58、src/client/ui/style.ts:1-27）：

- 宿主以 git/npm 装插件**不跑构建脚本** ⇒ 包必须发预编译 dist，不能指望消费方 build。
- client 产物是 `window.__ModuleLoader__.load({ id, factory })` 的 CJS 闭包，`import './x.css'`
  只会产出独立 css 资源、**内核不加载** ⇒ 样式只能以 TS 字符串 + 运行时注入分发。
- `react` / react-dom / `@deepseek-ai/*` primitives 走 PLATFORM_MODULES 白名单保留 `require()`；
  打进包里会产生第二份 React 实例（hooks 直接崩）⇒ 一律 optional peer + external。

**注入器工厂化（硬约束，非选项）**：现 `src/client/ui/style.ts:28,34` 是模块级单例 + 固定 style id
`dsh-task-dispatch-table-ui`，多插件同页必然互相覆盖 ⇒ 必须改成 `createStyleKit({ id, prefix })`，
style id 带插件前缀，token 前缀参数化。

**包形态裁决**：`dsh-plugin-core` 一个 npm 包 + 子路径导出（`./ui`、`./files`，重入口 `./files/codemirror`）。
曾考虑拆多包，结论是 tree-shaking 让拆包在产物大小上零收益，只多出双 tag / 发布顺序 / 跨包 peer 区间
的协调成本；规模变大到依赖区间互相打架、或 files 因宿主 API 频繁 breaking 时再拆（files 是头号候选）。
用户确认的模型：**安装 = 整包；使用 = 按子路径 tree-shaking**。

**边界（四方调研共识）**：

- 进：token 映射表（前缀参数化）、注入器工厂、基础控件（Segmented / Button / Input 家族 / Textarea /
  Checkbox / MarqueeText / Loading / SectionHead / BackToTop / LiveText / resizer）、日期时间、
  文件浏览、HTTP client 骨架、i18n 基建、宿主类型面 + 能力探测、官方 CSS-module 类名发现。
- 不进：`mirror/` 官方会话 UI 全家（`ui-style-guide.md:108,110` 已判定「不抽」，宿主升级三插件集体漂移）、
  业务 token（`--tdt-cal-*` / chip-bg / filechip / PROCESS_FILES_CSS）、TaskPicker、CodeViewer 审美、
  `PANEL_CONTENT_ID` 页面几何、任何插件私有路由 / DB 表、`@deepseek-ai/*` 运行时依赖。

**发布方式**：npm 公开包。私有包会让最终用户装插件时要配 token（GitHub Packages 上次就是因此被否），
且 npm 私有需付费；**公开 ≠ 开源**——发布物只是 `files` 指定的 dist，源码仓可以私有。OIDC 发布复刻现有
三个仓的 workflow 即可。包名 `dsh-plugin-core` 2026-10-18 探为空闲，**发布前再 `npm view` 复核一次**。
备选 `dsh-plugin-koc-core` 留作后备。

**`design` 要不要从 `ui` 里独立出来**（Q0 的子问题）：
- 独立：零 React 依赖，插件只想统一配色/尺寸但用自己的组件时，可以只引 `design` 不引 `ui`
  （对「服务未来所有插件」很关键——不是每个插件都会用我们的控件）；
  依赖方向单一，不会循环。
- 并入 `ui`：少一个入口，但把「只想用 token 的插件」也拖进 React。

**「Data」归哪**（用户提问）：两种含义分别落位——
「跟底层沟通 / 取数」⇒ `utils`（Q1 已定）；「控件要展示的数据怎么格式化」⇒ 也是 `utils`。
`ui` 只接收已经格式化好的值，不自己取数、不自己格式化。

**`host` 到底是什么**（2026-10-18 查证后解释给用户）：宿主 = DeepSeek Harness 内核本身，
插件跑在宿主进程里、`ctx` 由宿主注入。dispatch 里已存在的三样东西，就是 `host` 要装的：

- **宿主类型面** —— `src/host.ts` 自称「宿主最小类型面」：`SessionId` / `HostSession` / 消息块等 TS 类型，
  形状是**读 dsh 源码**得来的，且刻意不依赖 `@deepseek-ai/*` 运行时包（插件运行在宿主进程内）。
  不写就是 `any`，写就要去读内核源码 ⇒ 每个插件都要面对，抽出来一次写对。
- **能力探测** —— 实例：`file-browser.tsx:325` 的 `officeToPdf ?? null`（官方 office 转 PDF 可能没就位），
  判空后降级成「不可用」空态。不判空就崩。
- **官方 CSS-module 类名发现** —— `src/client/official-classes.ts`：官方 CSS module 由宿主运行时注入
  `document.head`，类名形如 `.EvIC1a_frame`（构建哈希 + 语义名），**哈希每次构建都可能变** ⇒
  写死会在某次宿主升级后集体失效，只能运行时按 `data-plugin-css` 解析发现，取不到回退自绘 + 告警一次。

**`design` 和 `ui` 的区别**（2026-10-18 用户复述确认无误）：`design` 是**值 + 注入机制**
（颜色/间距/字号/圆角/层级的 token、样式怎么挂到页面上、主题暗色），产物是 CSS 文本，
**零 React、没有组件、没有 input**；`ui` 是**用这些值搭出来的组件**（React 组件 + 交互逻辑）。

- 只想统一配色但自己写组件的插件 ⇒ 只用 `design`（自己写原生 `<input>` 再套我们的 token 样式，
  这种用法完全合法，不是错）。
- 要现成零件 ⇒ 用 `ui`：直接 `<Input />`，样式 / 错误提示 / 多语言提示全部自带，
  **不再自己写原生 input**（用户确认的预期）。
- 边界：`ui` 的组件是**纯零件，不自己取数**。像「选工作区的下拉框」这种要读工作区列表的，
  不属于 `ui`，属于 `explorer`（它依赖宿主数据）。

| `explorer` | VS Code 资源管理器：树 + 预览 | 形态最像（树形浏览 + 预览窗）；Windows 语境里 Explorer 就是文件管理器 |

**`host` 的定位澄清**（2026-10-18 用户问「是不是封装和宿主对接的能力，比如要调『去工作区』
就调包里的方法」⇒ **一半对，要澄清**）：

- **它不是「替你调宿主」**。宿主 API 是运行时由 `ctx` 注入的，`ctx` 在插件手里，包拿不到 ⇒
  包**不能**提供「去工作区」这种调用方法（除非插件把 `ctx` 传进来，但那会把包和宿主版本焊死，
  宿主一 breaking 包就得发 major）。
- 它提供的是**形状 + 探测 + 发现**：告诉你的代码「宿主给你的东西长什么样」（`SessionId` /
  `HostSession` / 消息块），「宿主现在有没有这个能力」（`officeToPdf` 之类判空降级），
  「官方 UI 的 CSS 类名现在叫什么」。**真正调用仍然是你自己拿 `ctx` 调。**
- 「去工作区」这种**具体功能**的封装属于 `explorer` 子包 —— 它内部用 `workspaceFiles.list`，
  但它拿到的 `workspaceFiles` 是插件传进来的（dispatch 里已经是 `WorkspaceFilesFace` 这个接口）。

**`ctx` 能不能传进去**（用户追问）：技术上能，但传整个 `ctx` = 让包去认识整个宿主 ⇒
宿主改一点，包就得跟着改 + 发版。更好的做法是 dispatch **已经在做的**：不传整个 ctx，
只传**需要的那一小块能力**（`WorkspaceFilesFace` 只暴露 list / stat / readBytes）⇒
宿主 breaking 时，改的是插件「取出那一小块」的一行，包不动；而且包可以用假实现单测。

**要不要 `host`**：**建议现在不做**，只挂在需求文档的「候选，未抽」里。理由：
（a）它跟宿主版本绑得最紧；（b）目前只有 dispatch 一家写过 `host.ts`，抽了就是
「把一家的形状当标准」，正是我们要避免的；（c）真痛点（类名失效、能力判空）现在只有一家碰到。
等第二个插件又写出一份 `host.ts` 时再抽，那时候有两份实例校准，抽象才靠得住。

**`explorer` 的范围**（用户原以为它只是「右边那个侧拉框」，需扩展）：
它是**「工作区 / 文件」领域包**，不止侧栏：

- `ExplorerPanel`：侧栏（目录树 + 面包屑 + 预览）—— 现状 `file-browser.tsx` + `file-preview.tsx`
- `WorkspacePicker`：选工作区（**现状不存在**，用户明确要做）
- `FilePicker`：选文件（未来）

放一起的理由：三者共用同一个数据源与同一套「加载中 / 错误 / 空态 / 降级」处理，
拆成两个包反而要各自重复注入一遍。

**「选工作区下拉框」的契约**（用户诉求：插件别管去哪取数据，只要告诉它单选/多选/上限）：

- **归属**：`explorer`。形态是下拉框，但数据是工作区 —— 它跟浏览面板是一家人。
  `ui` 里只有**纯下拉框** `Select`（不知道工作区是什么）。
- **落地方式 = 用户的解法 ①（传数据），而且实地查证显示基本是唯一可行的**：
  - 工作区列表在 dispatch 里是 **host 侧**取的：`src/dispatch.ts:35` `ctx.workspaceRegistry.list()`；
    再经**插件自己的** HTTP 通道送到 client：`src/client/index.ts:937-960`
    （body 里 `workspaces?: { title, anchorSessionId }[]`，还带 `degraded?: { workspaces?: boolean }` 降级标记）。
  - ⇒ client 侧组件**没法自己取**：数据要跨 host↔client 边界，那条通道是**插件私有**的；
    包要接管就得连通信层一起接管，太重。
  - ⇒ 契约：`WorkspacePicker({ workspaces, mode: 'single' | 'multiple', max, onChange })`
    —— **数据调用方给，交互组件全管**（单选 / 多选 / 上限 / 搜索 / 加载中 / 错误 / 空态 / 降级 /
    多语言提示，全在组件里）。插件省掉的是「怎么写这个下拉框」，不是「怎么拿列表」。
  - 现状对照：`file-browser.tsx:80,85` 的 `workspaces: readonly string[]` + `onPickWorkspace`
    已经是「外部传列表」的写法，只是它还长在面包屑里、没有独立成控件。

**「选大模型」放哪**（2026-10-18 用户提问建议放 UI ⇒ **该方案已推翻，改独立 `llm/` 子包**）：

用户反对「只做通用 Picker、让插件自己拼」，理由：**两个插件都要选大模型，这就是通用需求，该抽象**。
查证支持他 —— 两家都有，且**实现完全不同**：

| | dispatch | stp（`src/client/model-pair.tsx`） |
|---|---|---|
| 形态 | 单级下拉，值编码 `${provider}/${id}`（`index.ts:356,958`） | **provider + model 一行两个下拉** |
| 数据源 | 自己 host 侧 `/options` 回来（`index.ts:937-960`） | 远端 `llm/listProviders` + 各 provider 设置文档 profile 的 `models` 数组 |
| 默认项 | 「跟随宿主」一项（`editorFollowHost`） | 无 |
| 降级 | `degraded` ⇒ 显示「暂无可选」，**不回退反推** | 目录 loading / unavailable ⇒ **退回两个文本框**（fail-safe） |
| 为何自绘 | 通用下拉即可 | 官方 settings-form 只有文本/数字/密钥三种控件、**没有下拉**，
  只能用官方 `Menu` + `Button` 原语组合 |

⇒ 抽象面定三条：**数据调用方给**（两家通路不同，包不能替取）；
**形态统一**（provider / model 两级，含「跟随宿主」这类默认项由调用方注入）；
**降级口径统一**（现在是两家两种口径 —— 「暂无可选」vs「退化为文本框」，
必须收敛成一种或做成可配。这正是用户原始痛点「不标准、不知道抄得怎么样」的实例）。

**2026-10-18 用户推翻：不建 `llm/` 子包，`ModelPicker` 回 `ui`。** 用户原话「就为了选个大模型
建个包，它不是 UI 里的一种吗？那以后子包可多了」。**我同意，理由**：

- `ModelPicker` **数据由调用方给、自己不取数、没有持续长大的领域逻辑**，它就是一个控件，
  跟 `Select` / `Picker` 同类 ⇒ 进 `ui`。
- 之前推 `llm/` 是为了跟 `explorer/` 「领域对称」，那是**为了对称而对称**。
  对照：`explorer/` 有 ExplorerPanel + 预览体共 1600+ 行的实质内容，ModelPicker 没有 ⇒ 不该平起平坐。

**由此确立「什么才配独立成一个子包」的判据**（防止以后子包无限膨胀）：

> **独立成包的条件 = 它是一块有实质内容、会持续长大的「功能模块」；
> 只是一个控件 ⇒ 进 `ui`。**

配套三条：
- **按「功能模块」分，不按「控件类型」分**：弹窗 / toast / Loading / 下拉 都是**呈现形式**，
  不是立包的理由（用户原话：「那个对话内容只是我用 dialog 的方式去呈现」）。
- **按「功能模块」分，不按「业务领域名词」分**：不能因为叫「模型」就建 llm 包。
- 判断的硬指标（可操作）：**这一块有没有超过一个控件的工作量、会不会自己长出第二个 API**。
  `explorer`（浏览 + 预览 + 选文件）⇒ 是；`ModelPicker` ⇒ 否。

**`dialog` 包的定位据此收敛**：`Dialog` / `Modal` 控件本身可以留在 `dialog` 包（官方的调不了、
要自绘且要对齐官方外观，有实质工作量）；但**不得**因为「某个功能用弹窗呈现」就给它立包 ——
内容归内容（通用功能 ⇒ 功能包；插件业务 ⇒ 留在插件）。

**基础反馈类全部进 `ui`**（2026-10-18 用户拍板）：`Loading`、`toast`（用户点名），
以及同类基础反馈件（空态 / 错误边界 / 日志展示类组件）。它们都是「最基础的 UI」。

**`ModelPicker` 支持两种形态**（用户要求：有的地方先选厂商再选模型，有的地方一个下拉搞定）：

- 用一个**有意义的名字**切换，不许用 `style1` / `styleB` / 数字（用户明确反对）。
- 推荐 `variant: 'cascade' | 'flat'`（**级联**：先厂商后模型 / **平铺**：一个下拉列全部）。
  备选 `'provider-first' | 'model-only'`（更直白）、`'two-step' | 'combined'`。
- **数据统一为一种结构**：`groups: [{ value: provider, label, options: ModelOption[] }]`。
  `flat` 形态忽略分组、扁平渲染；`cascade` 形态先选组再选项 ⇒ 一份数据两种渲染，
  调用方不用为两种形态准备两套数据。

（被推翻的原方案：ui 通用 Picker、不造 ModelPicker —— 用户否掉，理由是「很多地方都要选大模型，
让它各自用通用选择器去做意义不大」。记录在案以免日后重新争论。）

**两条原则定稿**（2026-10-18 用户总结）：

- **统一到「控件」粒度就够了，不要提整个页面。** 用户原话：「我所有的标题都想统一，
  那我把标题做一个统一的控件、放在 UI 层不就完了吗？不需要把整个页面都提出来。」
  ⇒ 想统一某类元素（标题 / 按钮 / 输入框）⇒ 做成一个控件进 `ui`；
  只有「有实质内容、会持续长大的功能模块」才配独立成子包（explorer / session 这类）。
- **设置页骨架不搬**（用户拍板：「搬那个没有意义」）。作为候补挂着，等第二个消费者出现再说。

**⚠ 纠正一处理解：明暗色跟的是「宿主里的选择」，不是「系统设置」**（2026-10-18）：

用户以为「系统设明色我们就明色、系统设暗色我们就暗色」——**这是错的**。
`tokens.ts:196-197` 写得明确：

- 判据 = **`body[data-ds-dark-theme]`**，由**宿主启动脚本 `toggleAttribute` 写入**
  （源码核实过），是**用户在 DeepSeek 客户端里的选择**。
- **插件禁止用 `prefers-color-scheme`** —— 原文理由：它跟的是**系统**，不是用户在宿主里的选择。

⇒ 两者会分叉：系统亮色 + 用户在 DSH 里选暗色时，跟 `prefers-color-scheme` 就会显示成亮色，
与宿主不一致。**搬 token 时判据必须写死 `body[data-ds-dark-theme]`。**

#### Q1 · 公用方法（日期 / 格式化）放 `./utils` 还是并入 `./ui`

**状态**：待定

- 独立 `./utils`
  - 好：ui 只管样式与控件，职责清；纯函数无 DOM 依赖，将来 host 侧（node）也能引；tree-shaking 干净；
    以后塞字符串 / URL / 防抖等纯函数不用污染 ui。
  - 坏：**「host 侧能复用」这条论据被查证推翻** —— dispatch host 侧要的是时区 / 计划刻度（`Intl` + cron），
    跟 client 的展示格式化不是一回事；stp 那个 host 侧 `pad` 是内联的、也没打算共用。
    另外为 `pad2` / `formatDateTime` / `formatBytes` **三个**函数开一个子路径入口 + 一份类型声明，性价比低；
    而相对时间文案又依赖 i18n，放进「纯函数 utils」并不干净（见 Q2）。
- 并入 `./ui`（README 现状写法）
  - 好：这三个函数的调用方几乎全是 UI（formatDateTime 给 DateTime / time-text 用，formatBytes 给附件卡用），
    跟着控件走改一处；相对时间文案本来就依赖 `LiveText` 控件 + `Translate`，放 ui 里不用跨包；少一个入口。
  - 坏：纯函数与 UI 耦合；将来若真有非 UI 的工具函数要进包，会越来越勉强（那时再拆 `./utils` 也不迟）。
- **推荐**：先并入 `./ui`（包内可以单独放一个 `format.ts` 文件，只是**导出**挂在 `./ui` 下）。
  判据：**调用方是不是 UI** —— 目前全是。等 utils 里出现第二个品类（http / string / 防抖）再开 `./utils`
  子路径，那时候拆的成本只是一个 exports 条目。
- **结论**（2026-10-18 用户拍板：**独立 `./utils`**，推翻上面的推荐）：
  1. **UI 保持纯粹**：`./ui` 只管样式与控件联动，不放格式化方法。
  2. **`./utils` 放通用方法**：日期处理、字符串处理等，与界面无关；按用户说法它还承担
     「和底层沟通、获取数据」这一类（⇒ 老边界清单里的 **HTTP client 骨架**归入 `./utils`，
     不再作为独立子路径候选，Q5 分期时跟着调）。
  3. **便于日后整体独立**：用户打算将来把 utils 再剥出去给非 DSH 的场景复用
     ⇒ 由此产生一条硬约束：**`./utils` 不得 import `./ui`、不得依赖 React / DOM / 任何宿主 API**，
     只能依赖标准库与注入的参数（见 Q2 的 `t`）。否则将来剥不干净。

#### Q2 · 多语言谁负责

**状态**：已定（2026-10-18 用户拍板）

- 证据：`time-text.ts`（相对时间）与 `file-browser.tsx`（t: Translate）都**已经**是「由 props 注入 `t`」的写法，
  不是 import 一个全局 i18n 实例。三家各自有 `locales.ts`，文案 key 各不相同。
- 方案 A：包不碰 i18n，所有需要文案的 API 都收一个 `t: Translate` 参数（`type Translate = (key, vars?) => string`）
  - 好：包零 i18n 依赖，现在就能搬 `time-text` 和 `file-browser`；三家的 key 各不相同也不用统一；
    跟现有写法完全一致，改造量最小。
  - 坏：调用方每次都要传 `t`，样板多；包内控件的默认文案（比如「加载中」）也要调用方供给。
- 方案 B：包自带 i18n 基建（内置中英字典 + Provider）
  - 好：调用方省心；包内控件有默认文案。
  - 坏：三家现有文案要迁字典，工作量不小；包一旦内置字典，加一种语言要发版；老边界清单里
    「i18n 基建」是**进**的，但排期在最末（v3）。
- **推荐**：A。包只定义 `Translate` 类型并一律由 props 注入；内置字典留到真有人抱怨再说。
  ⇒ 这样 Q1 里「相对时间依赖 i18n」不再是阻塞项：相对时间（`relativePast` 这类）本身是纯函数，
  收一个 `t` 参数即可进 `./utils`，不违反 Q1 定的「utils 不碰 UI / 不依赖 i18n 实例」的硬约束。
- **结论**：**核心提供什么，核心就负责它的多语言。**
  - 包内控件自带的**固定提示语**（校验错误、加载中、空态、确认/取消这类）由包内置字典（至少中英）
    + 一个语言设置入口（初始化时 `setLocale`，或探测宿主语言）解决，插件不用管。
  - **插件自己界面的文案由插件自己管**，包不接管、不提供插件级 i18n 框架。
  - 分界线：控件显示的是**调用方传入的业务数据**（任务名、文件名）⇒ 不翻译；
    控件自带的**固定提示语** ⇒ 包翻译。
  - 例：核心的日期控件自己会说「请选择有效日期」（包管）；插件表单里「任务标题不能为空」（插件自己管）。
- **遗留**：`./utils` 里需要文案的函数（相对时间）要不要也是包内置一份？
  按本结论「核心提供的就核心负责」⇒ 包内置，但同时保留传 `t` 覆盖的口子（Q1 的注入约束不冲突）。
