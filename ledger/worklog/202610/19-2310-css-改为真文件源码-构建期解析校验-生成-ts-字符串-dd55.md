## Background

起因不是“CSS 想换个写法”，是 2026-10-19 那一整天的事故复盘。

事故本体（`20261019-1604-…-823a` / 提交 `dbfbccf`）：`src/design/tokens-css.ts` 的模板字符串
结尾多写一个反斜杠（`\`` 而非 `` ` ``），字符串内容因此多出字面反引号，落在 tokens 与控件
样式的交界处；CSS 解析器把它当不合格选择器开头，一路吞到下一个 `{` ⇒ 紧随其后的
`.dshpc-seg` 的**整个选择器**被污染成匹配不到元素的怪选择器。规则仍在 CSSOM、不报错、
不告警，只是永不生效 ⇒ `display:inline-flex` 从未落地、轨道退化成 block。

该 bug 已修复（`dbfbccf`），但用户不接“把这一个洞堵上”这个交付：

- 原话精神：**不是要改动最小，是要最健壮**；要最成熟、最正规、最容易维护的架构。
- 担心的不是这次，是“我不会预知下一次”——手工拼字符串的写法保留了整类失败模式的入口，
  今天堵反引号，明天还可能是别的字符/别的转义。不接受“遇到一个耗一天”。

所以本任务是**架构改造**：消除“CSS 以手工 TS 模板字符串承载”这个失败模式类别，而不是修 bug。

真源与约束：

- 宿主到底 complaining 什么：`docs/design/external/dsh-host.md` §1 / §1.1 —— 插件产物是
  `window.__ModuleLoader__.load` 的 CJS 闭包，**内核不加载任何 css 资源**，`import './x.css'`
  出来的文件没人用 ⇒ 运行时形态**必须**是字符串注入。这条不能动。
- 但它只约束“产物”，不约束“源码”：源码完全可以写真的 `.css` 文件，构建期转成字符串。

### 为什么不照抄官方

官方 `?inline`（`deepseek-harness/packages/client/tsdown.client.ts`，配合 `lightningcss` + 虚拟
模块 `\0dsh-css:`）能成立，是因为他们有整套基础设施：tsdown 打包器、lightningcss 转换、
CSS Module 类名哈希、同一个 `.css` 要同时服务「哈希类名导出」和「inline 字符串」两种用法。

我们只有「字符串」这一种用法。照抄用法而不带基础设施，得到的是一个**不完整的版本**：唯一收益
（真 `.css` 文件）A+ 同样有，而 dist 不可审、12 条测试断、tree-shaking 归零这些代价是白背的。
