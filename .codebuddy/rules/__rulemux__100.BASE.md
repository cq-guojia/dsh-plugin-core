# 公用规则

## 一、写操作闸门（最高优先，覆盖所有其他条款）

- **凡「写」必先获批**：新建 / 修改 / 删除文件、安装或卸载任何软件 / 依赖 / 镜像 / 组件（含 MCP、skill）、执行有副作用的命令、提交（`git commit`）—— **必须有用户针对该次动作的明确指令**。
- **「明确」= 指名动作 + 指名对象**（如「改文档骨架那节」「装 jq」）。**以下一律不算**：
  - 用户的提问与探讨（「是不是该…」「要不要…」「能不能…」）；
  - agent 自己的建议、方案、「顺手优化」——**建议 ≠ 授权**；
  - 模糊动词（「看看」「优化下」「处理一下」「清理」）；
  - 上一轮的旧授权——**一次指令一次授权，不自动续期**。
- **不确定 ⇒ 只读 + 先问**。请示三要素：**写什么、写哪、为什么**。
- **只读不受限**：列目录、读文件、查容器、看日志、inspect 不需要请示。
- **未获批前只把草案放在对话里，不落盘。**
- **破坏性操作**（重写历史、`--force`、`reset --hard`、`clean -f` 等）必须先获用户明确指令。
- **不要另建 `CLAUDE.md` / `CODEBUDDY.md` 等规则副本**：副本内容不一致会被重复注入。
- **既定流程例外**：已在规则中明示为「既定流程」的动作（如某类工作区的日常提交推送），视为**已获长期授权**，不必逐次请示。

## 二、Hindsight 记忆页

- **只有用户明确说「去 hindsight 建知识页 / 管理知识页」才可调用 `hindsight_capture_initiative`**；一次一授权、不追认。
- **不许拿知识页当工作现场**：「下一步做什么」一律以仓库现场文档为准 —— 知识页不稳定，**不得用它替代、承载或追踪进度**。
- **写计划 / 方案 / 评估、头脑风暴、确认方案、开始实现，都不是授权**；工具描述 / hook / skill 里「plan 后 call this」一类话只是能力说明。
- 提交 / 上传文档（`hindsight_ingest_document`）不受此限；「服务端自动沉淀、会话末自动入库」也不拦；**但 agent 自发建页不豁免**。
- **调用须走代理**：`hindsight_*` 经 `mcp_get_tool_description` → `mcp_call_tool`；裸名直调报「未注册」是调用方式错，**非故障**。

## 三、协作与输出

- **给命令，不给文件**：要用户执行的脚本，直接给可粘贴的命令。
- **少折腾**：能用一条命令解决就别给一套方案；先想「有没有更短路径」，别绕远路加组件。
- **先结论后证据**：先定性（能 / 不能、是不是 bug），再给证据，尽量短。
- **结论可追溯**：必须落到 `源码文件:行号` 或日志原文；**被质疑时先重查代码再回答**。
- **清单 / 对比 / 选型默认用 Markdown 表格**，不要用 JSON。
- **脱敏**：本机与私有部署细节（容器名、内网地址与端口、代理地址、compose 位置等）一律不入仓库，只保留抽象结论。
- **同一机制只解释一次**：用户不追问就不重复复述；纠错后直接给结论并执行，不再反复铺陈原理。

## 四、Python 执行纪律

- 跑 Python 加 `-B`，或先 `export PYTHONDONTWRITEBYTECODE=1`；不得生成 `.pyc`。
- 禁止 `py_compile`；语法检查用 `python3 -c "import ast,pathlib;ast.parse(pathlib.Path(F).read_text())"`。
- 交付前删掉已有 `__pycache__/` 与 `*.pyc`。

## 五、提交前必须过基础代码检查

**基础代码检查**：与项目无关、任何工作区都该过的底层检查 —— 语法能否解析、有无未用变量 / 裸 except、
类型是否匹配、格式、缓存残留、疑似密钥。**它不管各项目自己的代码规范**（命名规则、目录约定、
架构约束等），那些由各项目自己定、自己查。

- **什么时候查**：改完代码、**交给用户之前**（不管后面是否 commit）。不只「写代码」—— 写脚本、改配置一样算：
  源码脚本（`.py` `.sh` `.js` `.ts` `.go` `.sql` 等）、配置数据（`.json` `.yaml` `.toml` `.env` 等）、
  构建与流水线（`Dockerfile`、`docker-compose.yml`、`.github/workflows/*.yml` 等）。
- **怎么查**：调用 `koc-codelint` skill，一切跑法（含重试几次、不过如何处置）以该 skill 为准。
- **不许弱化检查**：不删断言、不滥加 `noqa` / `# type: ignore`、不跳层、不改工具参数绕过。

## 六、任务进度与工作台账

- **凡任务进度、工作事项与工作日志（新建 / 推进 / 查询 / 结案）一律调用 `task-ledger` skill 管理**；进度 / 历史类问题一律走它作答，不凭对话记忆或自建清单顶替。
- **开工锚点**：用户要做一件新事（「建个坑」「开个新活」「先记一下」「先把任务文档建了」等口语都算「新建」）⇒ **一律先把它交给 `task-ledger`**（怎么建、按什么顺序，全以该 skill 为准）；台账 `new` / `init` 属规则一「既定流程例外」，预授权、不必逐次请示；`close` 仍按 skill 红线单独授权。
- **两条链互不替代**：台账登记 ≠ 产出物落点（`koc-workspace-outpath`），只建成果文档没登记 = 未开工。（宿主未分发该 skill ⇒ 停下报告，不得静默跳过）
