# DSH 插件类规则

## 一、包产物入库

- **`dist/` 提交进仓库**：dsh 生态以 git 安装、pnpm 不跑构建脚本，装完即用。
- **任何代码变更推送前必须 build，并把最新 `dist/` 一并提交**，否则用户装到旧产物。

## 二、宿主机（DSH）接口

- 涉及 DSH 接口一律**先读源码与文档，再动手**，禁止靠运行时试探猜 API。
- 顺序固定：**① 先查项目 `docs/design/external/`（已核实的源码级事实）→ ② 找源码读实现 → ③ 仍无结论才问用户**。
  - 本地先找（`node_modules/@deepseek-ai/*`、宿主安装目录）；本地没有就上网拽：`npm view @deepseek-ai/<包> dist-tags` 取与宿主一致的版本，再 `npm pack @deepseek-ai/<包>@<版本>` 下载解包，直接读 `lib/*.js`。
  - **要读到实现本体**（方法签名、判空、抛错分支），不是只看 `.d.ts`；报错栈里的 `client.js:行号` 就是精确坐标。
- ⚠️ **禁止**：凭方法名猜签名后反复真机试错；也禁止「一次把候选全埋探针刷日志」——**要的是读源码，不是加探针**。

## 三、数据真实

- 界面上展示的任何数据（token 用量、时间、状态、计数……）必须来自宿主 / 官方数据面或自有存储的**真实值**；不得编造、占位或「先放个假数据看看效果」。只有用户**明确要求**「做个效果看看」时才允许 mock，且必须在代码与交付说明里标注是模拟数据。

## 四、验证

- **改动先过冒烟**（如 `npm run smoke`，直接测 `dist/` 产物）；发布 / 推送前另跑类型检查（如 `npm run typecheck`）。
- 具体命令由各项目 `package.json` / `AGENTS.md` 给出。

## 五、提交节奏

- **只走 `main`（主干开发）**：不要为每个功能开分支。只有大改 / 试验性改动（可能推倒重来、或中途不该被真机装到的）才临时开分支，稳了合回 `main`，用完即删。
- **功能改完即提交推送**：build + 冒烟通过 → `commit` + `push` 一次做完，**不必逐次请示**。
- **推送即发布**：别人能从 git 装到 `main` 上的东西，可能正是你正在改的代码（这一点已接受）⇒ **`main` 必须任何时候都 build 得过、冒烟得过**；先过门槛，再推。
