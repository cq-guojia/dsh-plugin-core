# 开发类工作区规则

## 一、接手入口

新会话 / 新 agent 一律按此顺序进入：

| 顺序 | 读什么 | 回答什么 |
|---|---|---|
| 1 | 项目根 `README.md` | 这是个什么项目 |
| 2 | `task-ledger` skill 的 `list`（在办任务） | 现在有哪些在办任务 |
| 3 | `task-ledger` skill 的 `history`（已结案） | 以前做过什么 |
| 4 | `docs/README.md` | 这个项目的文档实际怎么摆 |

- 进度类信息一律只扫索引（`list` / `history` 默认不含正文），要细节再打开 skill 给出的过程文档，不全文通读。**路径与格式以 `task-ledger` skill 为准，本规则不复述。**
- **第 4 步不能省**：本规则允许项目自定部分槽位的路径，不看 `docs/README.md` 就不知道实际文件在哪。
- 顺序**不得各项目另起**；缺哪个**先报告用户，经确认再补齐**。

## 二、落位

**槽位 = 每个项目必须回答的一类文档问题。** 下表一行一个槽位，「落位」一列给出它允许出现的位置。

文档只建在 `docs/` 下（根 `README.md`、`AGENTS.md` 及技术栈强制的元文件除外）。

| 槽位 | 落位 |
|---|---|
| 文档规范 | `docs/README.md`（**路径固定**） |
| 任务进度（在办 / 已结案 / 过程叙事） | **不入 `docs/`** —— 由 `task-ledger` skill 统一管理（路径以 skill 为准）；不得在 `docs/` 内另建进度文档 |
| 运行逻辑 | `docs/design/architecture.md`（**路径固定**） |
| 功能总索引 | `docs/design/features.md`（**路径固定**） |
| 各功能 | `docs/design/features/` 内，一功能一文件（文件名项目自定） |
| 外部事实 | `docs/design/external/` 内，一主题一文件（文件名项目自定） |
| 数据库说明 | `docs/design/` 内（**路径与文件名项目自定**） |
| 样式规范 | `docs/design/` 内（**路径与文件名项目自定**，可为多个文件） |
| 方法规范 | `docs/design/` 内（**路径与文件名项目自定**） |
| 样例 | `docs/examples/` 内（**路径与文件名项目自定**） |

两个词的含义：

- **路径固定**：路径由**本规则或它托管的 skill** 给出，所有项目一致。不得改名、不得挪位、不得另建副本。
- **项目自定**：只能落在上表写明的那个目录内；**可以是单个文件、多个文件或子目录**，但不得跑到 `docs/` 之外。所有实际路径必须登记在项目 `docs/README.md` 的槽位表里 —— **未登记 = 不存在**。

其余约定：

- 项目可**追加槽位**（追加同样登记进 `docs/README.md`）；**不得改任何「路径固定」的槽位**。
- **不适用的槽位保留整行**，在「落位」列写 `不适用（原因）`，**不要删行**：上表是本规则定义的全集，**缺行 = 没回答**，agent 无法区分「不适用」和「漏了」。
- **命名表角色不表时间**：不带日期、不带版本号；纯 ASCII 小写 `kebab-case`；版本历史交给 git。
  - **例外：任务号与过程文档文件名**（都承担排序职责）。由 `task-ledger` skill 生成，格式与归档规则见 skill；**不要手拼**。

三个路径固定的设计槽位各装什么：

- **运行逻辑**：系统级分层、边界、触发关系、不变量。不写业务规则与接口细节；**放不下时怎么拆由项目 `docs/README.md` 定**，规则不预设子结构。
- **功能总索引**：有什么功能、对应哪个文件。**真源若在别处（OpenAPI / 路由表 / 代码）就不要再写一份 md**。
- **外部事实**：真源在项目仓库之外的已核实行为，带权威来源标识 + 适用版本 / 日期 + 稳定定位符。

## 三、真源

| 信息 | 真源 |
|---|---|
| 项目是什么、怎么进 | 根 `README.md` |
| 本项目有哪些槽位、各自实际路径 | `docs/README.md` |
| 在办任务的状态、owner、任务号、过程文档路径 | `task-ledger` skill 的状态表 |
| 某任务的过程、证据、结论 | 状态表 `worklog` 字段记的那个文件 |
| 已结案索引 | `task-ledger` skill 的历史层（查询走 `history`） |
| 仍然有效的长期结论 / 系统事实 | 对应 `docs/design/` 槽位 |
| 流程、模板、schema、校验 | `task-ledger` skill |

**可变正文只有一个真源**；其余处只允许存标识、最小摘要和链接，不得复制正文。聊天记录不是真源。

要写样式、抽公共逻辑、改表、找功能时，**先查该项目对应文档**；没有或不满足，**先向用户提**，不要另起一套。

## 四、维护时机

- 默认**事件触发**：所述事实或约束变了就更新，且与触发它的变更处于同一变更集，**不事后补**。
- **外部事实**按权威来源的版本 / 修订变化复核；无版本信号时，复核事件由项目登记。
- 槽位路径或适用性变化时，同步更新 `docs/README.md`。

## 五、纪律

1. **owner 权限**：一个任务只有一个 owner，只有他能变更该任务；要动别人的任务先交接（怎么做由 skill 定）。
2. 一次操作只变更目标任务，不得顺带改动别的记录。
3. **不得自动 pull / rebase**（会改写用户的提交）；并发冲突交给 skill 处理。
4. 在办任务状态只以 skill 的状态表为准；issue / 看板 / 平台只能是由真源生成的镜像，**不得独立维护**。
5. **有拍板 → 结论与理由写进归属文档，不另建决策文件**（功能决策进功能文档、样式决策进样式文档…）。

## 六、开发通用

- **文档与代码冲突时，以源码现状为准**：先读源码确认「现在实际是什么」，**不得凭文档猜实现**；发现分歧**先向用户报告**，不得自行回改文档。

## 七、git

- **本类工作区的既定流程**：用户说「提交」= `commit` + `push` 一次做完，不必再问「要不要推」。
- **绝不替用户决定网络层面的 workaround**：不配代理、不改 remote、不动凭证链、不换协议。推不上去就**原样报告错误**，用户自己解决。
- **远端协议与地址属项目级信息**，写在该项目 `AGENTS.md`，**不得擅改**。
